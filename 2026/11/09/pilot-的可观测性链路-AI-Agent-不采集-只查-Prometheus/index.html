pilot 的可观测性链路：AI Agent 不采集，只查 Prometheus

0. 一句话结论

pilot 不采集任何指标，它只查 Prometheus。

它不认识”机器”，只认识一个 URL。所以”监控另一台机器”改的不是代码，是 Prometheus 的 targets 列表。

1. 三跳链路（两头都不直连）

谁发起 → 谁接收 → 数据落在哪：

环节 谁发起 谁接收 数据落在哪
埋点 业务代码里的 client 库 HTTP /metrics 进程内存（计数器/直方图）
抓取 Prometheus（定时） 被监控服务 /metrics Prometheus 的 TSDB
查询 pilot（被用户问题触发） Prometheus HTTP API pilot 内存里的 JSON 结果

一句话：pilot 是”读数据库的人”，Prometheus 是”采集并存储的人”，业务服务是”产生数据的人”。

2. 三步拆开看

第 1 步：服务暴露 /metrics

内容本质是一段 HTTP 明文文本，一行一个样本：

  • 谁来产生：Prometheus 的 client 库预埋的计数器、直方图等。
  • 业务代码改动量：极小，通常中间件里挂一下，不用每个 handler 手写。
  • 这步的产物：一个可以被 HTTP GET 的文本页面。

第 2 步：Prometheus 主动拉取

  • 采集周期 scrape_interval: 15s。
  • 每 15 秒对 targets 里的每个地址发一次 GET，把文本解析成时序样本写进 TSDB。
  • “捕捉”这个动作真正发生在这里，不在 pilot。
  • 当前 targets 只监控自己（这是能拿来讲的实证）：
    • Prometheus 自己（localhost:9090）
    • pilot 自己的 /metrics（host.docker.internal:8081）

第 3 步：pilot 用 HTTP API 查询

调用链从工具入口一路往下：

  • 工具入口 GetAlerts（模型调工具的地方）→ collector.GetAlerts → clients.GetAlerts
  • clients 里发两个请求：
    • GET /api/v1/alerts — 当前在 firing 的告警
    • GET /api/v1/query_range — 按时间区间查曲线
  • 配置里 Prometheus 地址是 localhost:9090；日志走 ES，trace 走 Jaeger。

拿到 JSON 之后才轮到 pilot 干活，判断逻辑在 collector 里拼 PromQL：

按 service 标签定位一个服务，值 > 0.8 就记一条 high_cpu 异常。

pilot 不知道你的业务代码长什么样，它只知道指标名和标签。

3. pilot 怎么把数据真正拿到手：三个 HTTP client

最容易误判的一点：pilot 里没有 Prometheus / ES / Jaeger 的 SDK，也没有数据库驱动。所谓”拿数据”，就是自己用 net/http 发请求，读响应体，json.Unmarshal。

启动时 NewDataCollector 从配置读三个 URL，各 new 一个 client：

  • PrometheusClient → observability.prometheus.url（localhost:9090）
  • LogClient → observability.log.url（localhost:9200）
  • TraceClient → observability.trace.url（localhost:16686）

每个 client 只有四样东西：baseURL、带 Timeout 的 http.Client、tracer、ctx。没有连接池管理、没有重试、没有认证——就是一个地址加一个 HTTP 客户端。这三个端口就是全部数据入口。

一次查询的固定五步

以 GetAlerts 为例：

result 是只声明关心字段的匿名 struct，其余字段直接丢弃。

数据形态：JSON 文本 → 匿名 struct → 自己的 types.AlertInfo 切片。

五个端点，只有”怎么拼请求”不同

查什么 方法 + 路径 备注
告警 GET /api/v1/alerts 只看 state == "firing"
指标曲线 GET /api/v1/query_range 参数 query / start / end / step
日志 POST /{index}/_search 请求体是 ES 的 DSL，不是 GET
链路 GET /api/traces/{traceID} 只能按 traceID 查，不能按服务查

两个值得讲的细节：

  • step 写死 60 秒：不管查 1 小时还是 7 天，都按每分钟一个点返回。查 7 天就是一万个点——这是明确的取舍（简单、可控，代价是长区间点数膨胀）。
  • 日志检索的关键词权重：message^3、service^2、trace_id，按时间倒序，size 就是传进来的 limit。

错误分两层，只判状态码会漏

  • 传输层：client.Do 失败（连不上/超时），或非 2xx 状态码 → 走 formatHTTPStatusError，把状态码和响应体一起带出来。
  • 业务层：Prometheus 可能 HTTP 200 但 status 字段不是 success（比如 PromQL 写错）。所以必须额外判 result.Status != "success"。

日志那边还有一个刻意的容错：索引不存在时返回空数组而不是报错（靠判断 404 + index_not_found_exception）。理由是日志索引没建不该拖垮整次分析。

结果最后怎么变回给模型看的文本

client 返回的是结构体，但模型吃文本。所以工具层最后要拼一遍：

结构体 → 人读的文本 → 再包一层 JSON 字符串 → 作为 tool 消息回到模型。这是整条链路唯一”面向模型”的地方，也是工具函数签名是 (string, error) 的原因。

一次异常分析会发三个请求，串行

AnalyzeAnomalies 的顺序是固定的：告警 → 日志（限 100 条）→ CPU 指标阈值。

而且单个数据源失败只打 warning 日志，不中断整次分析——Prometheus 挂了不代表日志里没线索。

4. 为什么是这个架构（因果链，一个逼一个）

  1. 用户要问”过去半小时 CPU 怎么涨的” → pilot 自己不存时序数据 → 必须有 TSDB，这就是 Prometheus。
  2. 机器挂了现场必须留住（挂了还得有最后几秒数据）、采集要固定频率 → 采集不能由”有人提问”触发 → 采集必须是独立常驻进程。
  3. 采集协议和查询协议是两套 → pilot 只实现查询（PromQL / HTTP API）→ 换监控对象只改配置，代码零改动。

再加一条设计收益：pull 模型下，同一个 Prometheus 的指标能同时喂给 Grafana、pilot 和其他系统；pilot 不需要装在被监控机上、不需要常驻、不需要任何权限。

代价也很清楚：没有 Prometheus，pilot 就是个什么都看不见的空壳。

5. “监控项目”到底监控什么（三层对象）

最小可监控单元不是”项目”，而是「一个会暴露 /metrics 的东西」。

  • 机器层（infra）：装 node_exporter → CPU / 内存 / 磁盘 / IO / 网络。靶机脚本造的 cpu/mem/disk/io 故障就在这层。
  • 服务层（应用）：应用暴露 /metrics → QPS、P95 延迟、5xx 比率、Goroutine 数。告警规则全在这层，例如：
    • sum(rate(pilot_http_requests_total{status=~"5.."}[5m])) > 0
    • histogram_quantile(0.95, ... route)) > 1
  • 日志与链路层：collector 调 QueryLogs 从 ES 捞错误日志；trace 走 GetTrace 查 Jaeger。

三段检查落在同一个函数里，顺序固定（AnalyzeAnomalies）：

顺序 查什么 数据源
1 status=firing 的告警 Prometheus /api/v1/alerts
2 error 级日志（限 100 条） ES / Loki
3 CPU > 80% 等指标阈值 Prometheus /api/v1/query_range

所以”接入一个项目来监控”只是最常见的一种形态；也可以是一台主机、一个容器、一个中间件（MySQL exporter / Redis exporter 都是同一套路）。

面试定位口径：pilot 是数据源接入型 AIOps Agent，不是 Zabbix 那种”装 agent 到被监控机上采集”的模型。好处是零侵入 + 复用 Prometheus 生态，代价是能力上限取决于你喂了哪些数据源。

6. 自观测闭环（pilot 自己也被观测）

pilot 不只消费观测数据，它也生产：

  • HTTP 指标 pilot_http_requests_total、pilot_http_request_duration_seconds、pilot_http_requests_inflight
  • 请求日志写 ES
  • trace 用 OpenTelemetry 的 OTLP HTTP exporter 上报到 Jaeger

Prometheus 的 targets 里那个 host.docker.internal:8081 抓的就是它自己。

面试验收点：“调完一次接口，指标/日志/trace 三样有没有真的产生”是可验证的，不是 PPT 上的。

7. 部署位置：不是”本机 vs 云服务器”，是”同机还是分开”

先纠正一个容易写错的假设：“localhost” 只是当前配置的取值，不是架构约束。 pilot 是无状态的，它只做一件事——往配置里那个 URL 发 HTTP 请求。所以改部署位置，改的只是这个 URL。

由此，”pilot 在哪跑”和”数据源栈在哪跑”是两个独立的决定，组合有四种：

组合 配置怎么写 适合什么场景
pilot 和栈同机 localhost:9090 调试、单机演示，最省事
pilot 本机 + 栈在服务器 服务器 IP，或 SSH 隧道成 localhost:9090 本机内存留给 IDE，吃内存的 ES 丢到服务器
pilot 在服务器 + 栈在本机 本机可达地址 需要公网访问 pilot，但数据源不想暴露
全部分开 每个数据源一个地址 生产形态，本来就不在一台机器上

三个真正要权衡的维度：

资源：开销的大头不在 pilot，在”这套栈有多大”。pilot 自己很轻；重的是时序存储 + ES（ES 一个就可能吃掉 1G 以上）+ Jaeger + Grafana。机器规格决定能不能全塞一台；塞不下就拆开，或者把重的组件换掉（比如日志用 Loki 替 ES）。

网络：跨机只有两种麻烦——端口怎么通（内网直连 / 公网放行 / SSH 隧道），和谁能访问（把 9090 直接开到公网是很危险的）。

故障注入：靶机和 pilot 同机，注入的 cpu/mem 故障会连 pilot 一起打挂，演示不干净；分开部署才能”靶机在崩，pilot 在分析”。

另外，要 7×24 演示，得有一台常驻、有公网可达性的机器；纯本机跑，关机就没了。

8. 面试怎么答（30 秒版）

pilot 自己不采集指标，它只做查询这一端。链路是三跳：被监控服务用 Prometheus client 库暴露 /metrics；Prometheus 每 15 秒主动拉取并写进它自己的 TSDB；pilot 再通过 /api/v1/query_range 和 /api/v1/alerts 两个接口拿到 JSON，按阈值判断异常。

之所以这么设计，是因为要回答”过去半小时发生了什么”就必须有时序存储，而采集必须独立于提问、固定频率地进行，所以拆成采集端和查询端。好处是 pilot 对业务零侵入，换监控对象只改 Prometheus 的 targets，代码不用动；代价是没接 Prometheus 就什么都看不见。

追问预案：为什么不装 agent 直接采集？→ 见第 5 节末尾的定位口径。
