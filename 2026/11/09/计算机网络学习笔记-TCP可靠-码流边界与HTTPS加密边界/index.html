计算机网络学习笔记：TCP 可靠传输、字节流边界与 HTTPS 的加密边界

零、主干速查

一次 HTTPS 请求里，三个协议各管一件事，别混着说：

  • TCP 管「字节可靠送达」：它看不见消息，只看见一串字节流。编号、ACK、重传、窗口，全是围绕「这串字节有没有完整、按序到达」。
  • TLS 管「这串字节不给别人看」：它把整个 HTTP 报文当载荷装进记录里加密，自己只额外暴露「送货必需的元信息」（IP、端口、SNI）。
  • HTTP 管「报文语义」：方法、路径、头、体，三代演进只是在解决「一个慢请求会不会堵住后面的请求」。

三个问题的标准落点：

问题 一句话答
TCP 怎么保证可靠 编号发现、ACK 确认、重传补救、窗口限速
数据在哪一层变成密文 TLS 记录边界：Application Data 是密文，记录之外都明文
HTTP/2 和 HTTP/3 差在哪 2 修了应用层排队，3 才取消传输层连坐

一、TCP 怎么保证可靠（四步是一条因果链，不是四个名词）

一句话本质：让发送方一直知道两件事——「对方收到了多少」和「对方还能收多少」。

因果链（每一步都是被上一步的缺陷逼出来的）：

  • IP 层会丢、会乱、会重复、会坏 → 所以要编号 + 校验和，让问题可见。
  • 但编号只能发现问题，发送方不知道对方到底收没收到 → 所以要 ACK。
  • ACK 自己也会丢，发送方不能无限等 → 所以要重传（超时重传 + 快重传）。
  • 拼命发、拼命重传会压垮接收方和网络 → 所以要窗口（rwnd + cwnd）。

用户原话（2026-11-07，QQ）：

我是这么理解的，嗯，tcp可靠首先就是。收和发。

收的话，要保证东西正确，那你得保证正确，你首先要有东西，怎么样确定你这个东西是有的呢？那就要靠序列号，序列号是保证顺序，那怎么样保证这个东西是正确的呢？就靠。校验和。

那发怎么保证可以呢，就是，靠确认号。如果对方给我发了，就说明对方真的有收到这么多的序列号。aCK向对方传达，我收到了。

因为各种不确定因素很多，如果没收到，那又需要继续有机制处理。所以如果丢了的话，对应有超时重传和快重传，快重传是到拥塞窗口，超时就是速度从1开始了。

超时解决了，最后一个就是。接和收的平衡。就是窗口的机制。

【补充】三处要修正：

  1. 序列号不只是保证顺序。它更像每个字节的身份证：丢了靠它发现缺哪段，乱了靠它重排，重复了靠它去重，重传也靠它定位。顺序只是其中一件事。
  2. 快重传不是「到拥塞窗口」。触发条件是连续收到 3 个重复 ACK；快恢复是把 cwnd 降到 ssthresh，然后进拥塞避免。
  3. 超时重传不只是「速度从 1 开始」。完整动作是 ssthresh = cwnd / 2、cwnd = 1、重新慢启动。漏了「阈值先减半」。

「收和发」这个框架比背五个名词好记：

  • 收的一方：保证内容对、顺序对、不重复 → 序列号 + 校验和
  • 发的一方：知道对方收到没、丢了补、别发太快 → ACK + 重传 + 窗口

二、TCP 与 UDP：边界归谁管

一句话本质：差别不在「可靠 / 不可靠」，在应用层交出的消息边界，传输层认不认。

因果链：

  • UDP 不干预应用数据 → 应用说这是一条完整消息，它就原样包一个数据报发出去，不拆、不合、不重排 → 边界被保留，代价是丢了没人管。
  • TCP 要管可靠性就必须对字节流动手：按 MSS / 窗口切段、按序交付、丢了重传 → 它眼里只有字节流，应用写了几次它不关心 → 边界丢失。
  • 边界丢了的后果叫「粘包」——本质不是 TCP 粘了，是你没告诉它怎么切 → 所以要自己加长度字段或分隔符做协议帧。

用户原话（2026-11-07，QQ）：

UDP 的”一个一个”不是它”主动拆”的，而是它不干预应用层的数据。应用层说”这是一个完整的消息”，UDP 就原封不动包起来发出去。它不做合并、不做拆分、不做重排——它把控制权全部交给应用层。

而 TCP 的”字节流”是它主动干预了：它会根据网络状况决定怎么拆、怎么合、怎么重传、怎么排序。应用层交出来的数据边界，TCP 根本不关心。

【补充】 UDP 自己不拆，但单个数据报超过 MTU 时 IP 层会分片，所以应用通常把单个数据报控制在 1200–1400B 以内。

三、rwnd 与 cwnd：谁能决定发多少

一句话本质：一个看接收方的杯子还剩多少，一个看网络管道现在能跑多少，实际能发的是两者取小。

维度 rwnd（接收窗口） cwnd（拥塞窗口）
谁决定 接收方 发送方自己
依据 自己缓冲区剩余空间 丢包、ACK 返回速度等间接推断
存在哪 TCP 报文头的 Window 字段，随 ACK 回来 只在发送方本地，报文里没有

用户原话（2026-11-07，确认版）：

rwnd 是 Receiver Window，接收窗口；cwnd 是 Congestion Window，拥塞窗口。

rwnd = Receiver Window：接收方告诉发送方”我还能接多少”。它由接收方决定，会写在 TCP 报文的 Window 字段里，随 ACK 一起发回给发送方。

cwnd = Congestion Window：发送方自己估算”网络现在能扛多少”。它只存在于发送方本地，不会出现在报文头里，是根据丢包、ACK 返回速度等间接推断出来的。

【补充】 收口一句：实际发送窗口 = min(rwnd, cwnd)。另外慢启动、线性递增、超时更新 ssthresh 这些动作，全部属于拥塞控制，是发送方在自己那一侧做的事，别和流量控制混。

四、HTTP 三代：堵在哪一层

一句话本质：三代都在解决同一个问题——一个慢请求 / 一个丢包，会不会把后面的请求全堵住。

因果链：

  • HTTP/1.1：一条 TCP 上响应必须按序回来，前一个慢，后面的排队 → 堵在 HTTP 层。浏览器只能多开连接绕过，所以 1.1 时代的优化都是「减少请求、多开连接」（雪碧图、多子域）。
  • HTTP/2：二进制分帧 + stream ID，让不同请求的帧可以交错发送、乱序到达，接收端按 ID 装回去 → 修好了应用层排队。但它仍然挤在一条 TCP 上，TCP 眼里只有一条连续字节流，丢一个包整条连接等重传 → 堵在 TCP 层。
  • HTTP/3：换成 QUIC（跑在 UDP 上），每条 stream 独立排序、独立重传，Connection ID 标识连接 → 才取消连坐，顺便带上 0-RTT/1-RTT、连接迁移、用户态实现的拥塞控制与 TLS 1.3。

一句话记：TCP 是连坐制，QUIC 是责任到人。

用户原话（2026-11-07，QQ）：

HTTP/1.1：一个请求发出去，要等回应回来才能发下一个，中间堵了后面就全卡住。浏览器还会限制同域名的 TCP 连接数（不是限制浏览器总数），所以优化思路就是减少请求、多开连接：多张图片合成一张雪碧图再切回页面各处、或者用多个子域名，等于多几条连接同时下载。

后来大家都要 TLS 加密，TCP 本来就要握手，TLS 还要再握手一轮。

HTTP/2 增加了帧，压缩了头，基本都搭配 TLS。

HTTP/3 把 TCP 和 TLS 握手整合，换成 UDP，解决队头阻塞。因为 TCP 是字节流，它不知道上面有几个请求、几条流，眼里只有一条连续管道，必须按顺序交付；而 QUIC 把 Stream 当成传输层的一等公民，每条流独立管理。

【补充】五处要修正：

  1. 1.1 不是第一版：0.9 起头、1.0 是第一个正式标准，1.1 是 1997 年修订。1.1 真正加的是 keep-alive 默认开、Host 头、chunked、缓存控制。规范里有 pipelining，但响应必须按序 + 代理易出错，浏览器默认关掉——所以准确说法是「实践上串行」，不是「规范上串行」。
  2. 队头阻塞必须分两层讲，这是这题的核心：1.1 堵在 HTTP 层；2 剥开了应用层排队但仍堵在 TCP 层；3 才让每条流独立重传。
  3. 帧不是「让东西有顺序」，是「让东西不需要顺序」：帧带 stream ID，可以和其他流的帧交错发送，接收端按 ID 装回去——这才叫多路复用。
  4. UDP 不是更可靠的传输，是不设门禁：不保序、不重传、不加密，重传 / 拥塞控制 / TLS 1.3 全是 QUIC 在用户态自己实现的。换 UDP 的真收益是绕开内核 TCP 栈的连坐 + Connection ID 做连接迁移（WiFi 切 4G 不断）。
  5. HTTP/2 的「更安全」不是 2 给的，是 TLS 给的；浏览器只在 TLS 上跑 h2，才让人误以为绑定。

五、HTTP 请求报文的四段

一句话本质：请求行决定「去哪儿、干什么」，头决定「我是谁、我要什么格式」，空行是分界线，体才是业务数据。

四段与顺序：

  1. 请求行：方法 + 请求目标（路径 + 查询串）+ 版本，如 POST /api/v1/chat HTTP/1.1。放在最前面，因为服务端只看方法和路径就能驳回请求（404 / 405 / 413），连「你是谁」都不必知道。
  2. 请求头：Host、User-Agent、Accept、Content-Type、Content-Length、Cookie、Authorization。身份在这一段。
  3. 空行：报文行和每个 header 各自以 \r\n 结尾，再多一个 \r\n 就是空行，它是头和体的分界线。没有 body 也必须有空行（GET 就是「报文行 + 头 + 空行」结束）。
  4. 请求体：JSON / 表单 / 文件；GET 通常没有。

用户原话（2026-11-07，QQ）：

报文分成请求行、请求头、空行、请求体。为什么请求行要在最前面？因为服务端拿到方法 + 路径就知道他那边根本没有你要的东西，可以直接驳回，甚至不需要知道你是谁。

想象一个人站着：头顶上是天空，天空就是请求行；去取快递要说你是取还是存（方法）、取的是哪个包裹（路径）、以及你选的哪个驿站（版本）。请求头是一系列说明信息，空行就是脖子，告诉对方这块结束了，请求体是真正的业务数据。

【补充】 三个必记点：

  1. 域名 / 协议 / 端口不在请求行，在 Host 头（HTTP/1.1 强制）——这是后面 SNI 明文的伏笔。
  2. header 必背五个：Host、Content-Type、Content-Length（与 Transfer-Encoding: chunked 互斥）、Connection、Cookie / Authorization。
  3. 预判追问：HTTP/2 没有请求行了，变成伪头部 :method :path :authority :scheme。

六、HTTPS 到底加密了什么

一句话本质：分界线只有一条——TLS 记录里的 Application Data 是密文，记录之外的一切都是明文。

  • 密文：整个 HTTP 报文——请求行、请求头、请求体、状态行、响应头、响应体。一个字节都不露。
  • 明文：IP 头（每跳路由都要读）、TCP 头（端口）、TLS 记录头（类型 / 版本 / 长度）、ClientHello（SNI、套件、随机数）、TLS 1.2 的证书（含域名与公钥）。
  • 反直觉点：TLS 1.3 把 ServerHello 之后（含证书）都加密了，明文只剩 SNI；用 ECH 连 SNI 也能藏。
  • IP 藏不住的原因：加密发生在传输层之上，每一跳都要读 IP 头。想藏 IP 只能再套一层（VPN / Tor）。

用户原话（2026-11-07，QQ）：

从请求头一直到响应体都被加密了，不加密的就是域名、公钥那些。

SNI = 客户端在 TLS 握手时告诉服务器「我要访问哪个域名」，让服务器能返回正确的证书。但它本身是明文的，所以域名会暴露。

IP 和端口没法加密，这是最底层的限制。路由器转发数据包靠的就是 IP 地址和端口，如果把 IP 加密了，路由器根本不知道往哪送，整个互联网就没法工作了。

【补充】 加密范围比「请求头到响应体」更靠前：请求行也在密文里，没有「头加密、行不加密」这种切法。「公钥明文」只对 TLS 1.2 成立，TLS 1.3 里证书已进加密握手流量。

七、HTTPS 比 HTTP 多了什么（三个目标，不是七样清单）

一句话本质：HTTP 是明文文本协议，谁都能看、能改、能冒充；HTTPS 在它下面垫了一层 TLS，把这三件事补上，HTTP 报文本身一个字没改。

三个目标各配一套机制：

目标 破的手段 补的机制
防偷看（机密性） 抓包读内容 对称加密（AES-GCM / ChaCha20）跑数据，密钥由非对称/ECDHE 协商
防篡改（完整性） 中间人改内容 每个记录带 AEAD tag
防冒充（身份） 假站点、中间人 服务器出示证书，由 CA 私钥签名，客户端用内置根证书逐级验到可信

外围补丁别和核心并列：HSTS（防 SSL stripping 降级）、OCSP / stapling（查吊销）、端口 443 + https:// scheme。

用户原话（2026-11-07，QQ）：

HTTPS 相比 HTTP，多了 TLS 协议层、TLS 握手、数字证书与 CA 信任体系、密钥协商、完整性校验、HSTS 和 OCSP 等机制，共用一把密钥加解密。

【补充】 覆盖范围对，但答成了清单，这是这题最大的失分点。面试官要听的是「为什么会多出这些东西」。另外「共用一把密钥」只说了结果没说来源：会话密钥是协商出来的，之后数据全走对称（因为快），TLS 1.3 严格说收发各一把。

八、为什么对称和非对称必须搭配

一句话本质：非对称负责递钥匙，对称负责干活，证书负责证明这把钥匙是谁的。

因果链：

  • 只用对称 → 密钥怎么安全送到对方？网上传就被截获，后面全白搭（密钥分发难题）。
  • 只用非对称 → 物理上装不下数据：RSA 2048 一次最多约 245 字节，而且慢几个数量级。它天生只能装一把密钥。
  • 所以分工：非对称只做一件事——把会话密钥安全递过去；其余数据全交给对称。
  • 现代做法更进一步：TLS 1.3 用 ECDHE，不是「用公钥加密密钥」，而是双方各出一对临时密钥、交换公钥、各自算出同一个共享密钥（密钥交换，不是密钥传输）。
  • ECDHE 的 E = ephemeral：临时私钥用完即弃 → 前向安全，服务器长期私钥日后泄露也解不开历史流量。
  • 闭环：非对称解决了「密钥怎么安全到对方」，没解决「这个公钥是谁的」→ 交给证书 + CA。

用户原话（2026-11-07，QQ）：

曲线、基点、公钥都可以公开，私钥是从私钥算公钥，不是从公钥算私钥，公钥是私钥的单向函数结果。

对称加密：一把钥匙，既能锁也能开，加密和解密用同一把密钥。优点速度极快，适合加密大量数据；缺点这把密钥怎么安全交给对方。代表算法 AES、ChaCha20。

非对称：一对密钥，公钥加密的数据只有私钥能解，私钥签名的数据公钥可以验证。就像邮筒，谁都能投信，只有主人能打开取信。

只用对称：密钥分发难题，直接传密钥被中间人截获，后续加密全白搭。只用非对称：慢了 1000 倍以上，没法用。

TLS 用非对称协商出对称密钥，再用对称传数据，这就是混合加密。

【补充】 三点：

  1. 「私钥推不出公钥」就是 ECDH 的地基，只差点破一句：所以不需要传密钥，双方各自算出同一把。「协商」和「传输」的区别，是这题从及格到高分的那一步。
  2. 「慢 1000 倍」换成更硬的约束：RSA 2048 一次最多约 245 字节，物理上装不下业务数据。
  3. 加密用对方公钥，签名用自己私钥；验签用对方公钥。

九、URL 与 SNI：域名有两份副本

一句话本质：加密的是 HTTP 的语义，不加密的是 把包送到目的地必需的元信息。

把 URL 拆开看 scheme://host:port/path?query：

  • path + query：只存在于报文里 → 加密。所以 path 里的 token、订单号别人看不见。
  • host：报文里那份加密了，但 SNI 明文泄漏（DNS 查询也能泄漏）→ 域名不保密。
  • port：443 在 TCP 头里，明文，能推断你在走 HTTPS。

为什么 SNI 必须明文：一台服务器（一个 IP:443）挂多个网站，TLS 握手在 HTTP 之前，服务器还没看到 Host，不知道该给哪张证书 → 客户端必须在握手第一步先报域名。选证书发生在密钥协商完成之前，加密还没谈好，它只能明文。

域名两份副本：Host 头那份在报文里（加密）；SNI 那份在握手时（明文）。抓包的人是从 SNI 拿到域名，不是从 URL 解出来的。

用户原话（2026-11-07，18:19 与 18:40）：

一部分，url 不加密，方法加密。

别人抓包，不能知道你访问了 shop.com 的哪个页面。

【补充】 「URL 不加密」错，但错得有价值——它其实指向了 SNI。准确说法是两句：知道你去哪个站点（SNI），不知道你访问哪个页面、带什么参数、用什么方法、传了什么 body。只答前半句会被追问「那他知道什么？」。

十、HTTPS 的路由转发在哪一层

一句话：三层转发看 IP，跟加密无关；四层负载均衡看 IP + 端口；七层路由看 path，必须先 TLS 终止解密。唯一例外是按 SNI 明文做域名级 passthrough（不终止 TLS）。
