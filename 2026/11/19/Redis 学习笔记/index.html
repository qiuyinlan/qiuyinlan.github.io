Redis 学习笔记

一、数据结构

1. String（字符串）

一句话本质：Redis 的 String 不是 C 语言字符串，而是用 SDS（Simple Dynamic String）实现的，解决 C 字符串的三大痛点。

为什么不用 C 字符串？

C 字符串的缺陷：

  • 长度获取慢：必须遍历到 \0，O(n)
  • 缓冲区溢出：修改时不检查空间，容易越界
  • 无法二进制安全：依赖 \0 判断结尾，不能存包含 \0 的数据

SDS 的解决方案：

SDS 的五种头部类型（省内存）：

  • sdshdr5/8/16/32/64：用不同大小的头部适配不同长度的字符串
  • 小字符串用更小的头部，减少元数据开销

SDS 的三大优势：

  1. O(1) 获取长度：直接读 len 字段
  2. 杜绝缓冲区溢出：修改前检查 alloc，自动扩容
  3. 空间预分配：修改后多留空间，减少后续内存重分配

String 的三种编码

编码 适用场景 特点
int 长整型数字 直接用 8 字节长整型存，最省空间
embstr 短字符串 SDS 和对象头在连续内存，少一次分配，读写快
raw 长字符串 SDS 和对象头分开分配，灵活但可能产生内存碎片

String 的应用场景

  • 整体缓存：经常整体读写的对象（如整个用户配置的 JSON 串）
  • 原子计数器：INCR/DECR 命令，适合点赞数、播放量、限流计数
  • 分布式锁：SETNX 命令（仅当 Key 不存在时设置）
  • 二进制安全：可存图片、序列化对象等任意二进制数据
  • BitMap：SETBIT/GETBIT 操作，用于签到等二值状态统计
  • HyperLogLog：PFADD/PFCOUNT，用于 UV 计数等基数统计

BitMap vs HyperLogLog：

  • BitMap：能精确查具体用户状态（如某天是否签到）
  • HyperLogLog：只估算总数，不记录具体是谁，有概率误判

2. Hash（哈希）

一句话本质：Hash 是”一个 key 管一堆 field-value”，专门用来存对象，比 String 存 JSON 更省内存、更精准。

Hash vs String 存对象

String 存对象：

缺点：改年龄要读整个 JSON、改完再全量写回去

Hash 存对象：

优点：

  • 精准修改：HSET user:1001 age 26，只改年龄，不用全量读写
  • 节省内存：Hash 底层对少量字段做了空间优化
  • 独立查询：HGET user:1001 name，直接取字段，不用解析 JSON

Hash 底层实现

  • 数据少、值短 → listpack（压缩列表），连续存储，省内存
  • 数据多或值大 → hashtable（哈希表），查找效率 O(1)

Hash 的应用场景

  • 用户资料：user:1001，存 name、avatar、status 等字段
  • 房间状态：room:2001，存 title、online_count、owner 等字段
  • 购物车：商品 ID 为 field，数量为 value

注意：Hash 是”一个 key 下面挂多个 field-value”，不是”很多个独立 key”。多个 field 共享一个 key 的开销，比用多个独立 key 更省空间。

3. List（列表）

一句话本质：List 是双向链表套数组的混合结构，兼顾增删速度和内存利用率。

Quicklist + Listpack 组合

Listpack（节点内部）：

  • 一块连续内存，按顺序存多个元素
  • 没有额外指针开销，比普通数组/链表更省内存

Quicklist（整体结构）：

  • 外面包一层双向链表，把多个 Listpack 串起来
  • 每个链表节点里装着一个 Listpack

为什么这样组合：

  • 只用链表：每个元素都存指针，太费内存
  • 只用大数组：中间插入/删除要搬数据，太慢
  • Quicklist：既保留链表增删快的优点，又利用 Listpack 的连续内存省空间

注意：这些不是 Redis 独有的，是通用的数据结构设计。Redis 的独特之处是把它们结合在特定数据类型上，并针对内存数据库场景做了极致优化。

4. Set（集合）

一句话本质：Set 是无序、唯一元素的集合，适合去重且无需排序的场景。

常用命令

  • SADD：添加元素（重复会自动去重）
  • SMEMBERS：查看所有元素（无序）
  • SISMEMBER：判断元素是否存在
  • SINTER/SUNION：求交集/并集

应用场景

  • 聚合计算（并集、交集、差集）
  • 点赞、共同关注、抽奖活动等

5. ZSet（有序集合）

一句话本质：Zset 是带分数的有序集合，底层用跳表保排序、哈希表保精准查，完美契合排行榜需求。

ZSet vs Set 核心区别

特性 Set ZSet
有序性 完全无序 按分数从小到大排序
元素 唯一 唯一（分数可重复）
操作 集合交并差 基于分数的排序、范围查询、排名计算

常用命令

  • ZADD key score member：存数据并打分
  • ZRANGE key 0 -1 WITHSCORES：按排名从小到大取
  • ZREVRANGE key 0 -1 WITHSCORES：按排名从大到小取（适合排行榜）
  • ZRANGEBYSCORE key 100 200：按分数范围取
  • ZINCRBY key 5 member：增减元素分数
  • ZRANK key member：获取元素排名

ZSet 底层实现

两种编码：

  • listpack：小型有序集合（默认元素数量≤128，单个成员≤64 字节）
  • 跳表 + 哈希表：超过紧凑编码限制后转换

为什么用跳表 + 哈希表组合：

  • 跳表：负责排序和范围查询（如取排行榜前 10 名），查找效率 O(log n)
  • 哈希表：负责精确查找某个成员的分数（如查某用户的具体积分），O(1)

为什么不只用有序数组：数组中间插入元素要移动大量数据，效率低。跳表通过多层指针，插入删除只需改指针，不用搬数据。

跳表详解

跳表是什么：有序链表 + 多层索引，用来替代平衡树，查找/插入/删除期望 O(log n)，实现比红黑树简单。

跳表节点结构：

层高怎么随机：

  • 节点从 1 层开始，每轮以 25% 的概率增加 1 层
  • 最多 32 层（ZSKIPLIST_MAXLEVEL）
  • 越往上节点越少，不需要维护严格的层级比例

跨度的作用：主要用于计算排名。查找成员时，把沿途经过的跨度累加起来，就能知道这个成员排在第几位，所以 ZRANK 不需要从头数到尾。

为什么 Redis 用跳表不用 B+ 树？

对比项 B+ 树 跳表
设计目标 为磁盘优化，减少 I/O 为内存优化，实现简单
节点结构 多叉平衡树，复杂 多层链表，简单
范围查询 需要中序遍历 顺着链表扫，天然友好
实现难度 节点分裂/合并复杂 随机层高，改指针即可

核心原因：

  • B+ 树为减少磁盘 I/O 设计，节点大且分裂合并逻辑复杂，在内存里反而浪费空间和时间
  • Redis 数据全在内存，不存在磁盘”翻页”慢的问题
  • 跳表在内存中读写快、实现简单、范围查询友好

跳表的应用场景（不仅 Redis）

  • Redis：zset（有序集合）
  • LevelDB/RocksDB：MemTable（内存表）默认是跳表
  • Java：ConcurrentSkipListMap/ConcurrentSkipListSet（JDK 自带）
  • 自研组件：时序数据库、网关、本地缓存、时间轮等

6. GEO（地理位置）

一句话本质：GEO 底层直接复用 Zset 实现，把经纬度换算成 Geohash 作为分数，地点名作为成员。

怎么工作的

  • 存：GEO 把经纬度换算成 Geohash（一个唯一的数字），作为 Zset 的分数；地点名字作为成员，调用 ZADD 存入
  • 查：利用 Zset 天然有序的特性，通过分数范围快速找出附近的点

为什么选 Zset：Zset 底层是跳表，天然支持排序和范围查找，完美契合”找附近”这种需求。

二、过期机制与内存淘汰

1. EXPIRE vs TTL

一句话本质：EXPIRE 是设定闹钟（设置过期时间），TTL 是看一眼现在几点（查看剩余时间）。

命令 作用 返回值
EXPIRE key 60 设置 60 秒后过期 1 成功，0 失败
TTL key 查看剩余秒数 正数=剩余秒数，-1=永不过期，-2=已不存在

注意：修改 key 的值会不会影响过期时间？

  • 普通 SET 覆盖值：会清除原来的过期时间（可用 KEEPTTL 保留）
  • INCR、HSET、LPUSH 等原地修改：通常保留已有的过期时间

2. 过期删除策略

一句话本质：Redis 用”惰性删除 + 定期删除”两道防线清理过期 key，在 CPU 开销和内存回收之间做平衡。

惰性删除

  • 什么时候删：访问 key 时检查有效期，发现过期就删除
  • 优点：只在需要时检查，不浪费 CPU
  • 缺点：如果 key 一直不被访问，会一直占内存

定期删除

  • 什么时候删：每隔一段时间（默认每秒 10 次）随机抽查一批 key
  • 怎么检查：从过期字典中抽样，如果过期比例高就继续检查，否则退出
  • 时间预算：默认每轮约 25ms，不会把所有 key 都遍历一遍

为什么不在过期时立即删除？

  • 过期 key 较多时，删除操作可能占用大量 CPU 时间
  • 在内存不紧张但 CPU 紧张的情况下，把 CPU 用于删除与当前任务无关的 key，会影响服务器响应时间和吞吐量

已经过期但还没删除的 key，能读到吗？

  • 不能。逻辑过期和物理删除是两回事
  • 主节点读取时会检查过期时间，发现已过期就当作不存在处理
  • 从节点依赖主节点传播删除命令，但对普通客户端读取也会根据过期时间判断

3. 内存淘汰策略

一句话本质：内存淘汰是在内存超过 maxmemory 时，根据策略选择 key 淘汰腾出空间；过期删除是清理已过期的 key，两者目标不同。

Redis 7.0 的八种策略

不进行数据淘汰：

  • noeviction（默认）：超过内存上限时拒绝写入，返回 OOM 错误（但过期 key 仍会删除）

在设置了过期时间的数据中淘汰：

  • volatile-random：随机淘汰设置了过期时间的 key
  • volatile-ttl：优先淘汰更早过期的 key
  • volatile-lru：淘汰最久未使用的（有过期时间的）
  • volatile-lfu：淘汰最少使用的（有过期时间的）

在所有数据范围内淘汰：

  • allkeys-random：随机淘汰任意 key
  • allkeys-lru：淘汰整个键值中最久未使用的
  • allkeys-lfu：淘汰整个键值中最少使用的

注意：如果选择 volatile 系列策略但没有可淘汰的过期键，写入仍然可能报 OOM。

LRU vs LFU

对比项 LRU LFU
关注指标 最近有没有用过 一段时间内用得多不多
实现方式 近似 LRU（抽样 + 候选池） 近似 LFU（概率递增 + 时间衰减）
适用场景 热点变化较快 热点比较稳定

Redis 的实现：

  • 没有维护严格的 LRU 链表，而是用近似 LRU
  • maxmemory-samples 控制采样数量，采样越多越接近真实 LRU，但 CPU 开销也越大

三、持久化

1. RDB vs AOF

一句话本质：RDB 是拍快照（某一时刻的内存数据），AOF 是记命令（所有写操作日志），两者各有优劣。

RDB 快照

怎么实现：

  • SAVE：主线程生成 RDB 文件，会阻塞（生产环境不用）
  • BGSAVE：fork 子进程生成快照，主进程不阻塞

优点：

  • 文件紧凑，适合备份和传输
  • 恢复时直接加载数据，通常比重放 AOF 命令快

缺点：

  • 故障时可能丢失最近一次成功快照之后的修改
  • fork 会短暂阻塞主线程
  • 生成快照期间如果写入频繁，写时复制会增加内存占用

AOF 日志

怎么实现：

  • 执行完写命令后，以追加方式写入文件
  • 重启时读取文件并逐一执行命令来恢复数据

三种写回策略（appendfsync）：

策略 说明 优点 缺点
always 每次写命令后都 fsync 刷盘 数据最安全 磁盘同步开销大
everysec（推荐） 每秒由后台线程 fsync 一次 通常丢失≤1 秒数据 磁盘卡顿时可能延迟
no 不主动 fsync，由操作系统决定 性能最好 数据丢失窗口难控制

AOF 缺点：

  • 纯命令格式的 AOF 通常比 RDB 大
  • 恢复时需要重放命令，耗时可能更长
  • AOF 损坏时可用 redis-check-aof 修复，但可能截掉部分数据

2. AOF 重写

一句话本质：AOF 重写是根据当前内存数据生成新的持久化内容，不是读取旧 AOF 再逐条合并命令。

为什么要重写：

  • 例子：先 SET counter 0，再 INCR 100 次，最后 counter 是 100
  • 重写时只需要生成”counter 等于 100”的命令，不需要保留所有历史操作

怎么实现：

  • 用 BGREWRITEAOF 手动触发，或根据文件大小和增长比例自动触发
  • 由子进程完成，主进程继续处理请求

版本区别：

  • Redis 7.0 之前：主进程把重写期间的增量写入 AOF 重写缓冲区，最后补到新文件
  • Redis 7.0 起：使用多部分 AOF，子进程生成新的 base 文件，主进程把变化写到新的 incr 文件，通过 manifest 切换

3. 写时复制（Copy On Write）

一句话本质：BGSAVE fork 子进程后，父子进程共享内存页；主进程修改某页时，操作系统才复制该页，让快照和修改互不干扰。

怎么工作的：

  1. fork 时，父子进程共享同一份物理内存页
  2. 主进程要修改某页时，操作系统复制该页，父子进程各自使用不同的物理页
  3. 子进程看到的仍然是 fork 时的数据视图

好处：

  • 省内存：fork 瞬间不复制所有数据，只有真正修改的才会触发复制
  • 省时间：fork 几乎瞬间完成，不阻塞主进程

注意：

  • fork 本身有成本（创建进程、复制页表），数据量大时会短暂阻塞主线程
  • 写入会增加内存占用（修改的共享页越多，COW 产生的额外内存越多）

4. 同时开启 RDB 和 AOF，重启时加载哪个？

正常情况下：开启 AOF 后，Redis 重启会优先使用 AOF 恢复数据（因为它通常保留更多近期变化）。

混合持久化（aof-use-rdb-preamble yes）：

  • AOF 的基础部分采用 RDB 格式，后续变化采用 AOF 命令格式
  • Redis 7.0 起，基础数据和增量命令分开保存，由 manifest 文件管理
  • 恢复时先加载基础数据，再回放增量命令，兼顾恢复速度和数据安全性

四、事务与原子性

1. 如何实现原子性？

一句话本质：Redis 单条命令天然原子（主线程串行执行）；多条命令需要原子性时，用 Lua 脚本或事务。

单条命令

  • INCR、DECR、SET 等单条命令执行时不会被其他客户端的命令插进来
  • 但应用层的”先 GET 再加一再 SET”是两个命令，中间可能被其他客户端修改

Lua 脚本

优点：

  • 把判断和修改放在 Redis 服务端一起执行
  • 执行期间其他命令不能插入，天然原子性

注意：

  • Lua 的原子执行不等于出错后自动回滚（前面修改成功，后面报错不会撤销）
  • 脚本应尽量先检查参数、数据类型和业务条件，再执行写操作
  • Lua 执行期间会占用主线程，不适合长时间循环或扫描大量数据

事务（MULTI/EXEC）

怎么工作：

  1. MULTI 开启事务，后面命令先进入队列
  2. 收到 EXEC 才按顺序执行
  3. 事务执行期间，其他客户端的命令不会插到事务中间

重要区别：Redis 事务不提供数据库事务那样的回滚机制

错误类型 处理方式
入队时出错（命令不存在、参数错误） EXEC 时拒绝执行整个事务
执行时出错（如 WRONGTYPE） 只有这条命令失败，其他命令仍会执行

2. WATCH 乐观锁

一句话本质：WATCH 是”盯着某个 key”，EXEC 时发现 key 被改过就放弃执行，由客户端决定是否重试。

怎么工作：

  1. WATCH key：先盯着这个 key（记住它现在的状态）
  2. 读取当前值，做业务判断
  3. MULTI：开启事务，把命令打包排队
  4. EXEC：提交事务时检查 key 是否被改过
    • 没变：事务正常执行
    • 变了：事务作废，返回 nil

通俗比喻：就像去餐厅点菜，先看好菜单（读取数据），然后告诉服务员你要做菜（WATCH+MULTI）。但在你最终下单（EXEC）前，如果厨房已经把菜做完了（key 被改了），服务员就会说”菜没了，重新点吧”。

注意：

  • WATCH 和事务命令要使用同一条连接
  • EXEC 结束后会取消监视，重试时要重新 WATCH
  • 竞争激烈时可能频繁失败，因此要有重试上限和退避

3. Pipeline（流水线）

一句话本质：Pipeline 主要用来减少网络往返和网络读写开销，不是事务，不保证原子性。

怎么工作：

  • 先批量发送命令，再批量读取结果
  • 适合互相独立的批量查询、写入

与事务的区别：

方式 主要解决问题 是否允许服务端判断
Pipeline 减少网络往返和系统调用开销 不能
MULTI/EXEC 多条命令连续执行，避免其他命令插入 命令先排队，不能直接拿前面的结果决定后面的入队命令
Lua 把判断和修改放在服务端一起执行 可以

注意：

  • Pipeline 批次不能无限增大（Redis 需要缓存响应）
  • 请求超时后可能无法确认哪些命令已经执行，重试时要考虑幂等

4. 事务 vs Lua 怎么选？

对比项 事务 Lua
原子性 执行过程不被打断，但无回滚 天然原子，执行时其他命令全排队
逻辑能力 只能一条条顺序执行 支持 if/else、for 循环
网络开销 需 3 次交互（MULTI/命令/EXEC） 只需发一次脚本
适用场景 简单命令打包 需要条件判断（如库存扣减）

五、线程模型与网络

1. Redis 为什么单线程？

一句话本质：Redis 瓶颈不在 CPU，在内存和网络；单线程无锁、无上下文切换，代码简单且性能极高。

Redis 单线程的优势：

  • 内存操作极快（微秒级），单线程就能扛住高并发
  • 无需加锁，无锁竞争问题
  • 无上下文切换开销
  • 单线程天然保证命令的原子性

对比 MySQL：

  • MySQL 磁盘 I/O 慢，需要多线程并发读写提升吞吐
  • MySQL 需要利用多核 CPU，避免查询互相阻塞

2. Redis 6.0 多线程

一句话本质：Redis 6.0 只对网络 I/O 开启多线程，命令执行仍然是单线程。

为什么加多线程：

  • 随着网络硬件性能提升，Redis 的性能瓶颈有时出现在网络 I/O 处理上
  • 单 Reactor 单进程无法充分利用多核 CPU

注意：不要误解 Redis 有多线程同时执行命令。命令执行仍然是单线程。

3. 网络模型

Redis 6.0 之前：单 Reactor 单线程模式

  • I/O 多路复用（epoll）监听多个连接
  • 主线程处理读写、命令解析、执行

Redis 6.0 起：网络 I/O 多线程

  • 网络读写由多个 I/O 线程处理
  • 命令解析和执行仍由主线程完成

注意：epoll 通知的是 Socket 的就绪状态，不会替 Redis 解析命令或执行命令。如果主线程执行了一条很慢的命令，其他客户端仍然需要等待。

六、主从复制与高可用

1. 主从同步

一句话本质：全量同步是”重新传一份完整数据”，增量同步是”从断点处接着传”，取决于复制历史还在不在。

全量同步（FULLRESYNC）

什么时候发生：

  • 首次建立复制关系（从节点没有复制信息）
  • 复制历史不匹配（主节点找不到兼容的复制历史）
  • 所需数据已经被覆盖（断连时间较长，缺失命令不在复制积压缓冲区中）

三个阶段：

  1. 从节点发送 PSYNC ? -1（表示没有可用复制信息）
  2. 主节点生成 RDB 快照（可写磁盘再传输，或无盘复制直接发送）
  3. 主节点发送快照期间的写命令，从节点加载 RDB 后执行增量命令

注意：replication buffer（给从节点发送复制数据用）和 repl_backlog_buffer（保留最近复制历史）职责不同。

增量同步（CONTINUE）

基于什么：PSYNC 命令，使用复制 ID（replication ID）和复制偏移量（offset）判断能不能接着同步

三个步骤：

  1. 从节点发送 PSYNC （offset 不是 -1）
  2. 主节点检查从节点请求的偏移量是否还在 backlog 保存的范围内
  3. 如果在范围内，从对应偏移量开始发送增量数据

repl_backlog_buffer：

  • 传统实现是环形缓冲区，Redis 7.0 使用共享的复制缓冲块
  • 默认 repl-backlog-size 是 1MB
  • 断连时间越长、复制流量越大，从节点需要的数据越容易超出这个窗口

怎么设置 backlog 大小：

  • 根据”每秒复制流量 × 希望容忍的断连时间”，再加一定余量
  • 例子：每秒复制流量约 2MB，希望覆盖 60 秒断连，至少需要 120MB

2. 哨兵机制（Sentinel）

一句话本质：哨兵是”监工”，负责监控主从节点、自动故障转移，保证 Redis 高可用。

哨兵的三大职责

  • 监控：不断探测主从节点是否健康
  • 选主：主节点故障时，从可用从节点中选出新主节点
  • 通知：通知其他从节点和客户端新主节点的信息

故障转移流程

1. 主观下线：

  • 每个哨兵定时发心跳包检测
  • 如果节点在 down-after-milliseconds 内没有回复，该哨兵标记它为主观下线

2. 客观下线：

  • 一个哨兵标记主观下线后，询问其他哨兵
  • 认为主节点下线的哨兵数量达到 quorum（包括自己），标记为客观下线

3. 选举 Leader：

  • 想成为 Leader 的哨兵请求其他哨兵投票
  • 每个哨兵在同一个纪元里只会投票给一个候选者
  • 获得票数达到 Leader 最低票数（quorum 和 floor(哨兵数/2)+1 的最大值）则选举成功

4. 选新主节点（按顺序比较）：

  1. 过滤不合适的节点（不可用、断连过久、replica-priority 为 0）
  2. 选择 replica-priority 数值更小的节点（数值越小优先级越高）
  3. 优先级相同，比较复制偏移量（更大的说明接收了更多复制数据）
  4. 偏移量也相同，比较 run ID（字典序更小的）

注意：这些条件是按顺序比较，不是选不到优先级最大的才去比较偏移量。

3. 脑裂问题

一句话本质：网络分区后，旧主节点仍被部分客户端当作主节点使用，而另一边已经完成故障转移，出现新旧两个主节点。

怎么发生的：

  • 旧主节点和哨兵、从节点之间的网络断了
  • 但某些应用还可以访问旧主节点
  • 哨兵把从节点提升为新主节点
  • 新旧两个主节点都可能收到写请求
  • 网络恢复后，旧主节点被改成从节点，它独有的写入可能被新主节点的数据覆盖

怎么降低影响：

  • 限制孤立主节点的写入：通过 min-replicas-to-write 和 min-replicas-max-lag
  • 让客户端及时发现新主节点：使用支持 Sentinel 的客户端
  • 减少共同故障：哨兵和主从节点分布在不同故障域

注意：这些措施能缩短风险窗口，但不能承诺完全消除数据丢失。

4. 主从能保证数据一致性吗？

不能保证强一致，因为 Redis 的主从复制默认是异步的。

典型场景：

  • 客户端往主节点写入一条数据，主节点返回成功
  • 但这条数据还没有复制到从节点
  • 这时主节点宕机，哨兵把从节点提升为主节点
  • 新主节点上就没有这条数据了

读写分离也有类似问题：刚写完主节点，马上去从节点读取，可能读到旧值。

缓解方式：

  • 对”写完马上读”的场景，优先读主节点
  • 用 WAIT 等机制等待副本确认
  • 用 min-replicas-to-write、min-replicas-max-lag 限制副本状态不好时的写入

注意：这些措施不会把 Redis 变成强一致系统。

七、Redis Cluster

1. Cluster 是什么

一句话本质：Redis Cluster 通过 16384 个哈希槽把数据分散到多节点，解决单机内存不够和单点故障问题。

哈希槽怎么计算

  1. 根据 key 按 CRC16 算法计算一个 16 bit 的值
  2. 再用 16bit 值对 16384 取模，得到 0~16383 范围内的模数
  3. 每个模数代表一个哈希槽

槽位分配

  • 平均分配：cluster create 命令自动把所有哈希槽平均分布到主节点
  • 手动分配：cluster meet 建立连接，cluster addslots 指定每个节点的槽

注意：

  • 真实的 Redis Cluster 固定有 16384 个槽，不能改成其他数字
  • 默认 cluster-require-full-coverage 为 yes，需要全部槽可服务
  • 槽位只分配给主节点，从节点复制对应主节点的数据，不独立分配新的槽

2. 客户端怎么知道访问哪个分片？

一句话本质：客户端先获取”槽位 - 节点”映射表缓存到本地，访问 key 时算槽位、查缓存找节点。

流程：

  1. 客户端和集群中任意节点建立连接
  2. 通过 CLUSTER SLOTS 或 CLUSTER SHARDS 获取映射关系
  3. 把映射关系缓存到本地
  4. 访问 key 时：
    • 对 key 做 CRC16 哈希计算
    • 对 16384 取模，算出哈希槽位
    • 查本地缓存的映射表，找到对应节点地址
    • 直接访问这个节点

遇到槽位迁移或故障切换：

  • MOVED：表示当前槽位应该访问另一个节点。客户端重发请求，并更新这个槽的路由
  • ASK：通常出现在槽位迁移过程中，只要求这一次请求去目标节点。客户端在目标节点先发送 ASKING，再发送原命令，不能据此永久修改槽位映射

3. CROSSSLOT 错误与 Hash Tag

一句话本质：Redis Cluster 的许多多 key 操作要求所有 key 位于同一个哈希槽，Hash Tag（大括号{}）就是用来强行聚集指定 key 的。

为什么会报 CROSSSLOT

  • Redis Cluster 规定，单条命令只能操作同一台机器上的 key
  • 如果要用事务或 Lua 脚本同时改多个 key，它们必须在同一个槽
  • 如果 key 分属不同槽，就返回 CROSSSLOT 错误

Hash Tag 怎么用

  • Redis 计算槽位时，只对花括号内的内容（activity:1001）做哈希
  • 所以这两个 key 会落在同一个槽里

注意：

  • 在同一个节点，不等于在同一个槽（一个节点会负责很多槽）
  • 不是所有 key 都应该使用同一个 hash tag（否则会把数据和流量集中到一个槽，失去分片意义）
  • hash tag 应该按需要原子处理的业务范围来设置（如一个活动或一个订单）

4. Cluster 的优缺点

优点：

  • 容量和吞吐量可以扩展：多个分片可以并行处理各自的请求
  • 支持故障转移：主节点故障时，可以由合适的从节点接替
  • 可以在线扩缩容：通过迁移哈希槽及其数据，调整节点负责的数据范围

缺点：

  • 维护更复杂：要管理主从关系、槽位、迁移、客户端路由
  • 多 key 操作受限制：事务、Lua 脚本以及许多多 key 命令，要求相关 key 在同一个哈希槽
  • 不能解决所有热点问题：一个 key 仍然只属于一个槽、由一个主节点处理
  • 存在复制延迟和数据丢失窗口：主从异步复制，故障切换不能保证强一致
  • 只支持数据库 0：不支持通过 SELECT 切换多个数据库

八、缓存三大问题

1. 缓存穿透

一句话本质：查的数据本来就不存在，根本不会失效，每次请求都打到数据库。

解决方案：

  • API 入口校验：判断参数是否合法
  • 缓存空值：对不存在的数据缓存空值标记，设置较短 TTL
  • 布隆过滤器：快速判断数据是否存在，不存在就直接拦截

布隆过滤器详解

一句话本质：布隆过滤器是”快速排重筛子”，专门用来判断”某数据绝对不存在”。

怎么工作的：

  • 像一个漏斗，里面有很多小格子（位图）
  • 存入数据时，经过多个哈希函数把数据打碎，把对应格子标记为 1
  • 查询时：
    • 如果有任何一个格子是 0 → 数据绝对不存在
    • 如果全是 1 → 数据可能存在（有小概率误判）

重要特性：

  • 布隆过滤器的位只能从 0 变成 1，绝不会从 1 变回 0
  • “判断不存在”一定不存在；”判断存在”只是可能存在（哈希冲突可能造成误判）

2. 缓存击穿

一句话本质：一个热点 key 失效，大量请求同时打到数据库。

解决方案：

  • 互斥锁：保证同一时间只有一个线程更新缓存
  • 逻辑过期或提前刷新：数据到期后由一个请求异步刷新，其他请求暂时用旧值

3. 缓存雪崩

一句话本质：一堆 key 一起失效，大量请求同时打到数据库。

解决方案：

  • 过期时间加随机数：避免集中失效
  • 互斥锁：保证同一时间只有一个请求重建缓存
  • 预热和后台刷新：提前加载热点数据
  • Redis 故障时：用高可用、熔断、限流、降级限制数据库回源并发

4. 缓存更新策略

一句话本质：先更新数据库再删除缓存（不是更新缓存），但仍有旧值回填的风险。

为什么删除缓存比更新缓存好？

更新缓存的问题：

  • 请求 A（110）和请求 B（120）并发写缓存
  • 因为网络延迟，A 可能后到达，把 B 刚写入的 120 覆盖了
  • 缓存变成 110，但数据库是 120 → 不一致

删除缓存的好处：

  • 请求 A 和 B 更新完数据库后，都把缓存删除
  • 有人去读时，发现缓存是空的，就去数据库读取最新的 120，写入缓存
  • 下次读取，缓存就是正确的 120

餐厅菜单板比喻：

  • MySQL 是后厨的真实菜单，Redis 是门口的小黑板
  • 更新缓存 = 后厨改完菜价后，服务员跑去门口把黑板上的价格擦掉，写上新的
    • 问题：两个服务员同时跑出去改黑板，后到的反而先写到，黑板最终是错的
  • 删缓存 = 后厨改完菜价后，服务员跑去门口把黑板上那道菜直接擦掉，什么都不写
    • 好处：两个服务员谁先到都行，第一个人擦掉了，第二个人到了发现已经擦了，再擦一下也没事

先更新再删，还会旧值回填吗？

会。典型场景：

  1. 请求 A 查询缓存未命中，去数据库读到旧值 100，随后停顿
  2. 请求 B 把数据库更新成 120 并删除缓存
  3. 请求 A 恢复执行，把读到的 100 写回缓存
  4. 最终数据库是 120，缓存却变成 100

缓解方式：

  • 如果业务能接受短暂旧数据，用较短 TTL 兜底
  • 必要时增加延迟删除，降低旧值回填的影响
  • 但延迟双删也不能当成强一致保证

九、分布式锁

1. 锁过期了业务还没执行完怎么办？

一句话本质：锁过期但业务没执行完，是因为业务执行时间超过了锁的过期时间。解决办法主要有锁续期和逻辑优化。

为什么会出现：

  • 锁的过期时间设得太短，而业务逻辑执行太慢
  • 导致锁在业务完成前就自动释放了，其他线程就能拿到锁，造成并发安全问题

怎么办：

  • 锁续期（看门狗机制）：启动后台线程监控快过期的锁，自动帮它延长寿命，直到业务执行完毕主动释放
  • 逻辑优化：把耗时长的操作移到锁外面，或者把过期时间设得比业务最长执行时间还长
  • 防误删：释放锁时，先检查锁是不是自己加的（通过唯一 requestId），避免删掉别人刚拿到的锁

2. 为什么要设置定时解锁？

一句话本质：定时解锁是为了防止死锁。

矛盾：

  • 超时太短：业务没做完锁就没了（并发安全问题）
  • 超时太长/没超时：万一挂了锁就永远打不开（死锁问题）

终极解法：看门狗（锁续期）：

  1. 加锁时不设固定长超时，而是设一个较短的默认值（如 30 秒）
  2. 启动一个”看门狗”后台线程，每隔 10 秒检查一次
  3. 如果发现业务还没做完，就自动帮锁续期 30 秒
  4. 等业务真正执行完，主动释放锁，看门狗停止

十、其他工具命令

1. INCR 原子计数器

一句话本质：INCR 是 Redis 的原子自增命令，让某个数字值 +1，多台机器同时加减不会错。

怎么用：

  • INCR mykey：如果 mykey 不存在，先初始化为 0 再加 1
  • DECR mykey：数字减 1
  • INCRBY mykey 5：数字加 5（指定步长）

为什么好用：

  • 原子性：多台机器同时让同一个数字加 1，不会像 String 那样出现覆盖错乱
  • 典型场景：文章点赞数、视频播放量、接口限流（统计每秒请求数）

2. UNLINK 异步删除

一句话本质：UNLINK 是异步删除，主线程把 key 从键空间中摘除后由后台线程释放内存，避免 DEL 大 key 时阻塞。
