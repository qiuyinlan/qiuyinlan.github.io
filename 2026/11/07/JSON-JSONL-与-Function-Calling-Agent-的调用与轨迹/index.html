一、JSON 与 JSONL

Q1. JSON 和 JSONL 有什么区别？

JSON 是一个完整的值，可以是对象也可以是数组，语法上必须括号闭合、能被整体解析。

JSONL（JSON Lines / NDJSON）是一行一个独立 JSON，行间用 \n 分隔。

三个必须记住的语法点：

  • 没有外层数组
  • 行间没有逗号
  • 每行末尾一个 \n

所以整份 JSONL 文件不是合法 JSON，json.Unmarshal 整个文件会报错；反过来每行单独拿出来都合法。

内存差异： 用 json.Unmarshal 解析 1GB 的 JSON 数组，内存里同时存在原始字节 + 解析结果，约 2 倍；JSONL 可以一行一行读，只留一行在内存里。

Q2. 为什么日志 / trace / 评测结果都用 JSONL？

四条，从强到弱：

  1. 追加友好。 JSON 数组要往 ] 前塞逗号，得 seek 到文件尾改，并发写直接打架。JSONL 就是 append，一行写完就完事。
  2. 损坏隔离。 写到一半断电，JSON 整个文件废；JSONL 只有最后一行残，前面全部有效，跳过坏行继续跑。这条对日志和 trace 是决定性的。
  3. 流式处理。 一行一行来，1GB 文件也能在小内存机器上处理完。
  4. 命令行直接能玩。 grep、tail -f、wc -l、jq -c 全部开箱可用。

JSON 数组得先 jq '.[]' 拆开，而且 tail -f 看到一个没闭合的数组啥也干不了。

  • 一行内不能有裸换行，字符串里的换行必须转义成 \n（encoding/json 会自动处理，手拼字符串会出事）
  • 不能有行尾逗号，{"a":1,} 非法
  • 不要在外面包数组，否则退化成 JSON，按行处理全废
  • UTF-8 无 BOM，带 BOM 会让只有第一行解析失败，是那种最诡异的 bug

Q4. 怎么选 JSON 还是 JSONL？

判断标准一条：这份数据是「一次性整体读」还是「一条条追加、一条条读」？ 后者一律 JSONL。

  • JSON：配置文件、API 请求/响应、需要整体结构的（ES 的 mapping、esapi.IndexRequest 的 body）
  • JSONL：日志、trace、评测结果、训练数据、批处理中间产物

落到 Pilot：

  • Redis 短期记忆存单个 JSON 字符串（一次取整个会话，用 JSON 合理）
  • ES 写入 body 是 JSON（一次请求一个文档）
  • 但 tool trace 落盘必须是 JSONL（每步追加一行，跑完几万行，还要被脚本批量读）

一句话：JSON 是一份文档，JSONL 是一叠同样的纸条——文档要好读，纸条要能一张张抽出来用。

二、Function Calling

Q5. Pilot 用 function calling 了吗？

用了，但一行相关代码都没手写——Eino 的 ReAct 全包了。

① 模型是 OpenAI 兼容协议（internal/ai/models/chat_model.go）

function calling 不是厂商私货，就是 OpenAI 协议里的 tools 字段，DashScope / DeepSeek 都支持。

② 字段名直接写了 ToolCalling（full_agent.go）

react.AgentConfig 里这个字段类型是 model.ToolCallingChatModel（eino v0.7.14 flow/agent/react/react.go），要求模型必须能发起工具调用。

③ 注册了 11 个工具（full_agent.go）：query_alerts、query_metrics、query_logs、search_knowledge…

④ 工具的 JSON Schema 自动生成（tools/knowledge_tools_impl.go）

InferOptionableTool 反射这个 struct，把 tag 转成 JSON Schema——这个 schema 就是 function calling 里 parameters 的内容。

Q6. Schema 是什么？是标准吗？

Schema = 结构说明书：用一份结构化描述，说明另一份数据长什么样。

数据库的 CREATE TABLE、Protobuf 的 .proto、JSON 的 JSON Schema，都是同一类东西。

JSON Schema 是公开标准，规范在 json-schema.org，有 IETF 草案版本（draft-07、2020-12），不是 OpenAI 私有格式。

用处有两个：给机器校验（不符就报错）+ 给人/AI 看（知道该填什么）。所以 function calling 拿它定义参数。

Q7. function calling 的定义是什么？

让模型不直接说人话，而是输出「要调哪个函数 + 参数是什么」这种结构化数据。

对比：

  • 传统：「你可以试试查看 payment 服务的日志，重点关注 error 级别……」→ 这是建议，还得自己解析，而且说法千变万化（查看日志/看看 log/检查一下日志），没法可靠解析
  • function calling：{"tool_calls":[{"function":{"name":"query_logs","arguments":"{\"service\":\"payment\",\"level\":\"error\"}"}}]} → 这是指令，json.Unmarshal 直接能用

三个必须理解的点：

  1. 模型不执行任何东西。 它只输出 JSON 说「我想调 query_logs」，真正查 Prometheus/ES 的是你的 Go 代码。模型只点菜，你炒菜。
  2. 模型的「知识」来自你给的 tools 列表。 不注册的工具它永远不可能调，它只看得到这次请求里塞进去的那份 schema。
  3. 结果必须回灌。 执行完包成 role:"tool" + tool_call_id 塞回消息列表，再调一次模型，它才知道查到了什么。

名字演化： OpenAI 2023-06 叫 functions / function calling，2023-11 改名 tools / tool calling。新名字支持一次返回多个调用（并行），也不限于函数。现在两者基本同义，前者是历史叫法。Eino 用的 ToolCallingModel / ToolsConfig 就是新叫法。

Q9. tool_calls 回给谁？谁去执行？

回给「发起请求的那个人」——在 Pilot 里就是跑在你自己服务器上的 Go 进程，具体是 Eino 的 ReAct 循环。模型只负责说，执行永远在你这边。

数据流向

模型那端从头到尾只是算出一段文本给你，它没有能力执行任何东西。

按执行顺序走一遍

第 1 步 模型返回 HTTP 响应。 远端返回 200，body 里有 tool_calls。这个响应回到的是发起请求的客户端——eino-ext 的 openai.ChatModel。

第 2 步 解析成 *schema.Message。 ToolCalls 字段带上 name、arguments、id。

第 3 步 ReAct 循环判断要不要调工具。 ToolCalls 为空 → 直接返回 Content（结束）；非空 → 交给 ToolsNode。

第 4 步 ToolsNode 按名字找工具（compose/tool_node.go）

这个报错就是「模型编了一个不存在的工具名」——它只看到你给的 schema，但偶尔还是会拼错或幻觉出一个不存在的工具。找不到就直接报错，不会瞎执行。

第 5 步 执行你写的那个 Go 闭包

这一步才真正产生副作用——发 HTTP 到 ES、查 Prometheus、读 Redis。全是你的代码在干。

第 6 步 结果包成 tool 消息回灌，再发一次请求给模型，它才知道下一步。

三个必须澄清的点

  1. 模型没有任何执行能力。 它不能读你的文件、不能访问网络、不能查数据库，唯一输出就是 token 流。
  2. 它也不知道你到底执行没执行。 模型是无状态的，每轮都是独立请求。不回灌结果，它只能瞎猜或重复调用。回灌不是可选项，是协议的一部分。
  3. 谁发请求谁收结果。 curl 手测就是 shell 脚本收，用 Eino 就是 Eino 收，用 LangChain 就是 LangChain 收。接收方永远是客户端。

不用框架的话，你自己就是执行者

Eino 的 react.NewAgent 就是把这个 for 循环、工具索引、结果拼接全封装了。

安全边界

既然模型能决定调什么函数、传什么参数，参数校验必须在工具里做。Pilot 每个工具都有 if query == "" 这类检查——不能因为「是模型传的」就默认合法。

一句话：模型的输出是「请求」，你的代码是「服务端」——它提议，你执行，结果再喂回去。

三、trace 落盘

Q10. 「落盘」是什么意思？

在第 3 步前后各插一个钩子，把当时看到的事实写成一行 JSON，追加到文件末尾。

不写数据库、不建表，就是文件——因为目标只是「事后能查、能统计」，文件最省事。

Q12. 实现时要注意什么？

  • 别在回调里做慢 IO。 这台机器是 40G 小盘，OnEnd 里直接 f.Write + fsync 会拖慢每次工具调用。用缓冲 writer + 定期 flush，或攒够 N 行再落。
  • resp_bytes 只记长度别记全文。 工具返回的日志动辄几十 KB，全存文件很快爆。要全文另存，trace 里放引用。
  • 这是评测的前置条件，但不只是为了评测。 线上排查「用户说答错了」时，能直接看到这一步调了什么、参数对不对，比看最终回答有用得多。

一句话：function calling 已经在用了（协议层），但工具调用的事实只活在内存里那几秒——落盘就是在它消失前多写一行。

四、串起来的因果链

  1. 模型协议里 tool_calls 是结构化 JSON → 所以能被机器比对（评测可行的前提）
  2. 但结构化数据只活在内存里，Pilot 的 ChatMessage 只存 role/content → 所以现在做不到工具级审计
  3. 要补 → 用 Eino 回调在工具执行前后各写一行 JSONL
  4. JSONL 而不是 JSON → 因为这是「一条条追加、一条条读」的数据，且要求断电只坏最后一行
  5. 有了这些行 → 才能算工具选择准确率、参数正确率、耗时分布，才能做 Agent 评测
