Agent 架构、Eino 内部机制与多 Agent 编排

零、主干速查（先看这个）

流程 A：Eino ReAct 一次往返（谁发起、谁执行）

流程 B：多 Agent 排障编排

关键认知：四个角色里只有 Synthesizer 调模型，前三个是普通 Go 代码在查数据。

一、Agent 框架与架构选型

Q1. 有哪些 Agent 开发框架？为什么用 LangGraph？

按编排模型分四类：

  • Chain 式：LangChain（LCEL）、LlamaIndex、Semantic Kernel、Spring AI —— 线性流水线，流程一复杂就打补丁
  • Graph 式：LangGraph、Eino（字节）、Temporal —— 节点 + 边 + 分支 + 状态，复杂 Agent 的主流方向
  • 多 Agent 自治：AutoGen、CrewAI、MetaGPT、Agno、OpenAI Agents SDK —— 角色互相聊，灵活但不可控、成本不可预测
  • 低代码：Dify、Coze、n8n、Flowise —— 快速验证，深度定制受限

LangGraph 真正值钱的四个能力：

  • Checkpoint 持久化：每步状态可存，崩了能续
  • Human-in-the-loop：节点中断等人审批（高危操作刚需）
  • 时间旅行：回放到任意一步改状态重跑
  • 节点级事件流：配合 LangSmith 看每步输入输出

代价：Python 为主（Go 服务要另起一个 Python 服务）、图要自己设计、设计不好比链还乱。

Pilot 为什么用 Eino：

  1. 语言栈：项目是 Go + GoFrame，LangGraph 是 Python，跨语言成本远大于收益
  2. Go 生态没第二个这么全的：组件层（ChatModel / Embedder / Retriever / Tool / Lambda）+ 编排层（compose.Graph）+ Agent 层（react.NewAgent）+ 可观测（callbacks）
  3. 图编排收益确实用上了：FullPilotAgent 不直接拼 messages，而是把输入清洗、知识检索、Prompt 模板、ReAct Agent 编成一张可执行图（full_agent.go）
  4. 运维场景要可预测：同样输入走同样路径、结论能溯源，比多 Agent 自由对话更合适

顺带：Eino 其实也有 checkpoint（compose/checkpoint.go），所以「状态持久化」这块它不比 LangGraph 缺，差的主要是生态和 HITL 的成熟度。

Q2. ReAct 和 Plan-Execute 的使用场景？

核心问题只有一个：「下一步做什么」由谁决定、什么时候决定。

ReAct（边想边做）

  • 结构：Thought → Action → Observation 循环，每轮重新判断
  • 优点：适应未知、能根据新信息调整、实现简单
  • 缺点：短视（容易打转）、无全局最优、token 不可预估、不可预测
  • Pilot 的 FullPilotAgent 就是：react.NewAgent + 11 工具 + MaxStep: 25

Plan-and-Execute（先规划再执行）

  • 结构：Planner 产出结构化 Plan → Executor 执行（可并行）→ 收敛
  • 优点：可并行、可解释、可展示进度、成本可预估
  • 缺点：计划可能错、需要 replan、首步延迟高

怎么选：

  • 根因未知、下一步依赖上一步结果 → ReAct
  • 步骤结构清晰、彼此独立可并行 → Plan-Execute
  • 要展示过程 / 要控成本 → Plan-Execute
  • 高危操作要审批 → 加 human-in-the-loop

Pilot 是分层混用：外层固定 Graph 编排 → 中层 Plan-Execute 排障流水线 → 内层 ReAct 补灵活探索。「确定性优先，灵活兜底」。

Q3. 有去中心化的 Agent 框架吗？用在哪？

先拆词，两种含义：

  • 控制层面：没有中心编排者，Agent 之间对等协商
  • 所有权层面：链上身份、自主结算、数据主权

三类代表：

  • 通信协议：A2A（Google 提，后捐 Linux Foundation，靠 Agent Card 做能力发现）、ANP（走 DID 身份）。注意 MCP 不是这类——它是 Client-Server 的工具协议
  • P2P 框架 + 市场：Fetch.ai 的 uAgents（链上地址 + Agentverse）、AGNTCY
  • 链上经济：Olas（原 Autonolas）

真实场景：跨组织协作（供应链 A 公司采购 Agent 直接和 B 公司库存 Agent 谈判）、调用第三方能力、Agent 市场结算、数据主权（医疗金融不出本地）。

为什么没普及：责任归属不清、跨组织 trace 没法透传、prompt injection 会跨 Agent 传播、没有 killer use case、多一轮协商延迟翻倍。

Pilot 不需要：单组织内部、数据和工具都在自己基础设施里、有中心编排者、不需要跨组织信任和结算。去中心化解决的是「信任和所有权」，这些都不存在。

Q4. Agent 之间是怎么交流的？

分三层，从紧到松：

  1. 共享状态（同进程）：往同一个对象写。Eino 里就是 state.Messages，成本最低，Pilot 里 90% 的「交流」是这层
  2. 消息传递（同系统跨协程/服务）：channel、HTTP/gRPC、Kafka/NATS
  3. 协议调用（跨组织）：A2A、ANP，需要身份发现和信任

Pilot 里三种实例：

  • ReAct 内部 = 共享 state，靠 tool_call_id 做调用与结果配对
  • 排障流水线 = 带缓冲 channel + WaitGroup，两个 executor 互相不知道对方存在
  • Executor → Synthesizer = 结构化数据（[]EvidenceItem 带 ID、来源、分数），不是自然语言，所以结论能溯源

多 Agent 四种协作模式：黑板（共享存储）、Supervisor（主管转派，最可控最常用）、点对点、辩论。

真正难的四件事：上下文裁剪（每传一次复制一份，token 指数涨）、消息格式统一（OpenAI 那套是事实标准，跨框架转换最容易出 bug）、trace 穿透（traceparent 一路带）、超时与幂等（有写操作必须幂等）。

Q5. sub-agent 怎么实现？为什么要做？

本质：把另一个完整的 Agent 包装成一个工具。 主 Agent 调它跟调 query_logs 没区别。

实现两个「不」：

  • 不传主 Agent 的 messages —— 子 Agent 从零开始，只有任务描述
  • 不回子 Agent 的完整轨迹 —— 只把最终结论给主 Agent

四个设计点：

  • 上下文隔离（最关键）
  • 结果只回摘要
  • 工具集最小权限（权限边界靠工具集划，不靠 prompt 求）
  • 超时和步数独立（子 Agent 打转不能拖死主 Agent）

为什么要用：

  • 上下文爆炸是硬理由：RAG 塞 20 篇文档进主对话，每轮重发，第 10 轮就是几十万 token。子 Agent 啃完只回 500 字结论
  • 专业化（不同 prompt/工具集/模型）
  • 并行（互不依赖的子任务同时跑）
  • 失败隔离（子任务挂了降级，不是整体崩）

Pilot 的诚实说法：严格说没有完整 sub-agent，但排障流水线里两个 executor 已经是简化版——职责单一、上下文隔离、结果摘要化，区别只在于它们是确定流程而不是自主 Agent。

什么时候不该用：工具少于 10 个、任务单一、子任务极短。判断标准：子任务的上下文体积是否显著大于结论体积。

二、Eino 内部机制

Q6. Chain 不能循环吗？图可以？

不是「不能」，是「循环在图里是原生表达，在 Chain 里得自己手写」。

  • Chain 语义是 DAG：A → B → C → 结束，进度由位置决定，没有回边的概念
  • 要循环只能自己写 for，然后自己补三样：状态累积、终止条件、死循环保护

图怎么表达循环：边允许指回前面（回边）。ReAct 内部就是：

代码在 react.go（ChatModel 出去的分支）和另一处（Tools 出去的分支，endNode = nodeKeyModel 就是回边）。

有回边就必须有上限：

  • Eino：compose.WithMaxRunSteps(config.MaxStep)，Pilot 设 25，默认 12
  • LangGraph：recursion_limit，默认 25，超了抛 GraphRecursionError

所有支持循环的图引擎都必然有这一步保护，否则模型一句「再查一次」就能让服务卡死。

真正差别是成本：Chain 手写循环要两百行 Go（状态、终止、计数、还没有可视化），用图是两个节点加两条边。

Q7. 「图是状态机」是什么意思？Chain 不是吗？

判据：下一步由「当前状态」决定 → 状态机；由「执行到第几步」决定 → 流水线。

  • Chain 是位置驱动：中间结果只是局部变量，散在栈上，框架看不见拿不到存不了
  • 图是状态驱动：节点只负责处理，核心是那份共享的、显式的 state

为什么显式 state 重要（不是术语游戏）：只有 state 可序列化，才有断点恢复、时间回溯、人工介入、可观测这四件事。Chain 里这些都做不了，因为「进度」= 程序计数器，没法序列化一个函数的执行位置。

Pilot 里两种图各占一边：

  • 外层 FullPilotAgent 的图是 DAG（无环），只是「带分支的流水线」，强在分支和多前驱汇合（AllPredecessor）
  • ReAct 内部的图才是真正的状态机：有回边、有状态累积、有终止条件

Q8. ReAct 的 state 结构体是什么？

flow/agent/react/react.go

Messages —— 整个 Agent 的记忆

  • 写：ChatModel 节点 append 模型回复，Tools 节点 append 工具结果
  • 读：下一轮 ChatModel 拿它当输入
  • 为什么必须有：模型无状态，第二轮能”记得”第一轮查了日志，靠的是这个数组被一起发过去了

ReturnDirectlyToolCallID —— 提前收工的标记

解决什么问题：某些工具的输出本身就是最终答案（get_current_time），再让模型加工一遍是浪费一次调用。

两种写入方式：

  • 配置声明：ToolReturnDirectly: map[string]struct{}{"get_current_time": {}}
  • 工具运行时喊：react.SetReturnDirectly(ctx)（react.go）

存 tool_call_id 而不是工具名，是因为并行调用时要精确标记是哪一次。

读取它的就是 Tools 之后那个分支函数（react.go）：非空 → direct_return → END，空 → 回 ChatModel。

Pilot 现状：ToolReturnDirectly 是空 map（full_agent.go），这条路没启用。

一个细节印证「state 可序列化」：react.go 的 schema.RegisterName[*state]("_eino_react_state")，注册类型名就是为了序列化/checkpoint。

Q10. Eino 为什么是中心化的？

中心化 ≠ 部署在一台机器。判据是：谁决定下一步、谁持有状态、节点能不能自主发起。

五个「中心」：

  1. 编译期中心：g.Compile() 把图编成一个对象，结构静态固定（full_agent.go）
  2. 调度中心：pregel 引擎决定谁跑、按 AllPredecessor / AnyPredecessor 判触发、统一计步（撞 MaxRunSteps 就停）
  3. 状态中心：state 是引擎持有的全局对象，节点只能通过 compose.ProcessState 读写，节点之间不直接通信
  4. 分支中心：AddBranch 的条件函数只返回节点名，由引擎去执行；节点不能自己跳转，只能”申请”
  5. 执行单元无自主权：Tools 是被动执行器，工具之间不通信、不协商、不能主动发起

跟去中心化对照三条：谁决定下一步（引擎 vs 协商）、谁持有状态（引擎 vs 各自）、节点有身份吗（没有 vs DID/Agent Card 可寻址）。

最关键第三条：Pilot 那 11 个工具出了这个进程就不存在，没有任何一个能被外部”找到”再调用。

三个澄清：

  • 中心化 ≠ 单机（可以多实例部署，但每个实例内部仍是中心调度）
  • 中心化 ≠ 不能断点恢复（Eino 有 compose/checkpoint.go）
  • 中心化 ≠ 不能并行（多 tool_calls 并行、两个 executor 并行）

收益：可预测、可测试、可观测、有硬上限、责任清晰。代价：单点、不支持跨组织、节点能力受限。这四条代价对「单组织内部排障」全都不构成问题，所以中心化是正解不是妥协。

三、Go 并发：channel 收结果

Q11. 为什么要用 WaitGroup？channel 不能替代吗？

因为 channel 只管「传数据」，不管「谁还没干完」——而 close 必须有人知道「全部发完了」才能调。

close 两条铁律：只能发送方调；只能在所有发送完成后调。

多个 goroutine 都在发时，谁是最后一个？没人知道 → 必须有个外部全局计数器，那就是 WaitGroup。

三个看起来能替代、其实不行的方案：

  • len(ch) == 2 → 瞬时快照，有竞争；轮询 len 等于手写劣质同步原语
  • 主协程数收了几条 → 必须精确知道总数，且放弃 range
  • 每个 goroutine 自己 close → 第一个关掉，第二个发送就 panic

纯 channel 也能做（done channel 收 N 次信号），但那是「自己实现一个功能更弱的 WaitGroup」。

本质分工：channel = 数据通道，WaitGroup = 生命周期同步。混在一起就得区分「这是结果还是完成信号」，代码变脏。

更省事的选项：errgroup，内部就是 WaitGroup + 错误收集 + ctx 取消。对「两个分支任一失败就该整体失败」的排障流水线更合适。

Q12. 计数器是 goroutine 跑完自动减一吗？

不是。全靠手动：wg.Add(1) 加，wg.Done() 减（等价 Add(-1)），wg.Wait() 只是阻塞等归零。

goroutine 退出，WaitGroup 一点感觉都没有——除非你在它退出前手动 Done()。

为什么写 defer wg.Done()：一定执行（panic 也跑）、不用管几条 return 路径、放第一行读代码的人一眼看到。

三个经典 bug：

  • 忘了 Done() → 永久阻塞（Go 里最常见的”莫名卡死”）
  • Add 写在 goroutine 里 → Wait 可能提前放行（必须在 go 之前）
  • Done 多调一次 → panic: sync: negative WaitGroup counter

Go 1.25 有 wg.Go() 自动 Add + defer Done，但 Pilot 的 go.mod 是 go 1.24.10，用不了。

Pilot 选带缓冲的理由：收集方天然要在全部结束后才处理，没有「边收边处理」需求。

四、多 Agent 编排（核心）

Q14. 多 Agent 编排是怎么跑的？

先点破关键事实：四个角色里只有 Synthesizer 真的调了模型，另外两个是纯 Go 查询代码，Planner 是规则。所以它不「智能」，是流程编排。

五个阶段：

① 入口 Orchestrator.Execute（orchestrator.go）

Orchestrator 只有四个字段：planner、executors map[Role]Executor、synthesizer、now func() time.Time（为了测试注入时钟）。

② 分诊 RulePlanner.Plan（routing.go）

  • 正则抽服务名（routing.go）：service=payment / service: payment，抽不到用默认
  • 三层关键词决定选哪些角色：知识类 → [Knowledge, Synthesis]；可观测类/故障类 → [Triage, Evidence, Knowledge, Synthesis]；都没命中 → [Triage, Knowledge, Synthesis]
  • 算 SkippedRoles：把没选中的显式列出来，表示”这里没查是因为不需要”

③ 并行执行 executeBranches（orchestrator.go）

三条不进 goroutine 的短路路径：

  • 没被选中→ StatusSkipped Step
  • executor 没注入→ StatusFailed + EXECUTOR_UNAVAILABLE
  • 执行报错→ StatusFailed + 一条 Limitation，另一个分支照常跑

④ 稳定排序：按 rolePosition（model.go：triage → evidence → knowledge → synthesis）排。

为什么必须排：channel 出来的顺序取决于谁先跑完，不排的话同样请求两次返回的数组顺序会不一样，前端渲染会抖。

⑤ 收敛：模型挂了不返回 error，走 fallbackAnswer()用确定性模板拼三段：Current conclusion / Missing data / Suggested next step。

「宁可给一份带缺口的证据摘要，也不编一个看起来很完整的答案。」

数据结构（model.go）：

  • Role：triage / evidence / knowledge / synthesis
  • Plan：Intent、Service、SelectedRoles、SkippedRoles、RoutingReason
  • Finding：Role、Summary、Evidence、Metadata
  • EvidenceItem：ID、Source、Content、Score、Metadata ← 可溯源的关键
  • Step：Role、Status、Summary、StartedAt、DurationMS、Metadata ← 前端画进度
  • Limitation：Role、Code、Message
  • Result：Answer、Plan、Steps、Findings、Limitations、Metadata

Step 的注释（model.go）：不暴露提示词或模型推理过程——这是边界意识。

三个设计决策：

  1. 分诊用规则不用模型：路由错的代价 > 慢一点；可测试（routing_test.go）、不抖动、省一次调用。代价是泛化弱，关键词硬枚举
  2. 分支隔离 + 显式降级：失败变成 Limitation 而不是抛错。降级不是隐藏问题，是把「哪些信息没拿到」显式交还用户
  3. 三个 interface 注入：Planner / Executor / Synthesizer 全是接口，测试能塞假实现

跟 ReAct 的分工：问知识、单点问题走 ReAct；查故障、要证据链走多 Agent。

四条不足（主动说）：

  1. 只并行了一层（evidence 内部查告警和查日志还是串行）
  2. 角色粒度太粗（没有独立的指标分析/链路分析角色）
  3. findings 没有跨角色消解（两份证据矛盾时让 Synthesizer 自己权衡，没做冲突检测）
  4. 可观测只到角色级（工具级 span 没接进去）

五、语言选型

Q15. 用 Go 写 Agent 有什么好处？

先承认：Go 不是写 Agent 的主流，主流是 Python。

Go 赢在：

  • 部署：单二进制，无运行时，镜像几十 MB（Python 几百 MB 起，加 CUDA 上 GB）
  • IO 密集型是主场：一次请求几乎全在等（模型 8~30s、ES、Prometheus），goroutine + context 超时取消最顺手
  • 流式：SSE + channel + bufio 很干净，Eino 的 StreamReader 底层就是 channel
  • 静态类型：工具参数是 struct，schema 由 tag 推导，编译期就能发现字段错误（Python 的 dict 要运行时才炸）
  • 可观测：Prometheus 客户端本身就是 Go 写的，/metrics 零成本
  • 中间件客户端成熟：ES/Redis/MySQL 都稳

Go 输在：

  • 模型侧生态为零：PyTorch、transformers、vLLM、微调、评测全在 Python，Go 只能调 API
  • 框架少：Agent 框架基本只有 Eino 一家完整
  • 迭代慢：改一行要编译（尤其调 prompt 时手感差）
  • 坑没人踩过：常常只能翻源码

正确判断是分层：Go 做服务层（网关、并发、工具执行、外部系统对接、可观测），Python 做模型层（训练、微调、评测、本地推理）。

什么情况别用 Go：要本地跑模型、要大量 prompt 实验、团队是算法背景。

Q16. 这个项目有大量请求吗？是网关吗？

不是网关，请求量也不大。 上一轮我说「高并发 IO 网关」是错的，纠正：

  • 网关的职责是转发，Pilot 没有下游业务服务可转发，它自己就是链路终点
  • 真实场景是一个运维团队，QPS 个位数到几十

Go 的优势不是「扛 QPS」，是「扛驻留并发」：

按 Little’s Law：并发连接数 = QPS × 平均延迟

  • 普通接口：20 QPS × 0.05s = 1 个并发
  • Agent 接口：20 QPS × 15s = 300 个并发

QPS 才 20，但同时 300 个连接挂着等 IO。 这才是 Go 真正赢的地方：300 个 goroutine 几十 MB，context 超时能掐断，SSE 长连接写得干净。

项目里真正「量大」的入口：知识库灌库（批量 embedding）、日志查询（一次几千条）、/metrics 抓取、cmd/e2echeck。

准确描述：低 QPS、高单请求成本、长连接驻留。

六、面试口径提醒

  • 别说「高并发网关」，会被问「你转发给谁」
  • 别说「多 Agent 是多个 Agent 互相聊天」，实际是「1 次模型调用 + 2 个数据查询 + 1 个规则路由」
  • 别说「有 sub-agent」，说「有 sub-agent 的隔离思想，但执行器是确定流程不是自主 Agent」
  • 去中心化那块：知道 A2A vs MCP 不是一回事，且明确说自己没有生产落地
  • 主动说出四条不足，比硬凑优点可信

七、工具调用到底怎么发生的（2026-11-09 补讲）

讲的是「模型说要调工具」到「本地函数真的被执行」之间的协议层：消息怎么传、谁解析、工具怎么被找到。

Q18. 为什么非要搞成消息？因为 HTTP 是无状态的

服务端不记得上一轮说过什么，所以每次请求必须把全部上下文重发一遍。”我想调函数”和”函数结果回来了”这两件事，也只能变成数组里的元素——否则模型下一轮根本不知道发生过什么。

由此得出一个反直觉但重要的推论：

所谓 Agent 循环 = 往同一个数组里追加消息、反复 POST。

一轮工具调用 = 两次模型请求。 这也解释了为什么工具返回的长文本会烧 token：整段结果都要塞进数组、每轮重读。

Q19. 工具怎么被找到？参数放在哪？

先点破：没有任何全局变量或注册表存参数。参数只在栈上活一瞬间。

执行顺序：

  1. 建表（启动时）：ToolsNode 把每个工具的名字和下标存进 map（indexes[toolName] = idx）
  2. 查表（运行时）：取 indexes[toolCall.Function.Name]，按函数名字符串查，不按顺序、不靠反射；查不到直接报 tool xxx not found in toolsNode indexes
  3. 透传：把 toolCall.Function.Arguments 原样（还是字符串）传给 InvokableRun
  4. 最后一刻才反序列化：InferOptionableTool 返回的是泛型包装器 invokableTool[T,D]，它的 InvokableRun 做三件事：

所以你闭包里的 input *QueryAlertsInput 是包装器塞进来的，代码全程看不到 JSON 字符串。

  1. 结果包装：返回的 string 被包成 ToolMessage(content, toolCallID)。toolCallID 是配对钥匙——一次可能并发调多个工具，模型靠这个 id 对上结果是哪次调用的。

QueryAlertsInput 这个 struct 被用了两次：启动时反射成 JSONSchema 发给模型（告诉它有哪些字段），运行时承接模型给的参数（反序列化的目标）。这是 jsonschema:"description=..." 这类 tag 的真正作用。

Q20. 那两个 Agent 是怎么分工的？一个走工具调用，一个不走？

先纠正事实：项目里不是两个 Agent 实现，是三个。

  • FullPilotAgent — Eino ReAct 图 + 11 个注册工具，走 tool calling
  • SimplePilotAgent — 手搓 messages、无任何工具，全项目无人调用（早期快速启动遗留）
  • Orchestrator（multiagent）— 角色化工作流，不走 tool calling

“multiagent 没用 Eino”这句也不准：它没用 Eino 的编排（react / compose），但用了 schema.Message 和 eino-ext 的 ChatModel。准确说法是”不用 Eino 的编排，只用它的消息结构和模型客户端”。

它怎么”处理工具”？答案是：根本不处理。

模型拿到的请求里没有 tools 参数，没有机会申请调工具。取数全由写死的 Go 代码完成，模型只在最后一步综合一次。

关键分界：它复用的是 collector，不是”工具”。

两条路在 collector 汇合，但工作流绕过了整个工具层。工具层干的活全是给模型用的（拼 schema、反序列化、把结果拼成人读文本再 marshal），工作流里没人读那份文本，所以整层不需要。

绕过之后必须自己补三样：

  • 参数变常量：写死 {"service": plan.Service, "status": "firing"}、now-30m、limit 10。没有模型，参数只能靠人定死。
  • 编排和容错手写：goroutine 并发 + 分支隔离 + 失败降级成 Limitation，这套在 tool calling 里是循环天然做掉的。
  • 输出改结构体：返回 Finding / EvidenceItem 而不是拼文本，因为下游要综合、要溯源。

所以一句话收口：tool calling = 函数 + 一层”让模型选函数、给参数”的协议外壳。去掉外壳，剩下的就是普通函数调用。

Q21. 什么时候必须加这层外壳？（判据）

看一句：“该调哪个函数、参数填什么”能不能穷举。

  • 不能穷举（用户可能问任何事）→ 必须加壳，让模型自己选。FullAgent 就是这种。
  • 能穷举（故障分析就那几条查法：查告警、查日志、查知识库）→ 加壳只换来不确定性和 token 成本。Orchestrator 就是这种。

配套的取舍：

ReAct + tool calling 固定工作流
谁决定查什么 模型 代码
灵活度 高，能走没预设的路径 低，只能走剧本
可复现 差，同问题可能两次路径不同 好
可测试 难，要 mock 模型 易，执行器是纯函数
成本 高，多轮调用 低，固定一次模型调用
溯源 弱 强（Evidence 带 ID + Source）

面试注意：被问”你项目里 Agent 怎么调工具”，必须先说清是哪个入口。笼统说”都是 ReAct 工具调用”，对方一看代码就知道没读透。

本节要点流水（自测用）

  • 工具调用在协议层就是一条 assistant 消息带 tool_calls 字段，arguments 是 JSON 字符串
  • 一轮工具调用 = 两次模型请求；Agent 的”记忆”就是那个不断变长的 messages 数组
  • Eino：启动建 name→index 表，运行时按名字查表，参数字符串原样透传，到 InvokableRun 里才反序列化
  • 参数不存任何地方，只在栈上；结果靠 toolCallID 和请求配对
  • 工作流复用 collector 而不是工具，因为工具层是专门为”给模型看”服务的
  • 判据：能不能穷举”查什么”，能穷举就别加壳

八、Agent 由哪几部分组成（六件 + 编排器）

一句话本质：Agent 没有唯一固定架构，不同框架拆法不同；但按「角色职责」拆，能拆出六个部件，再加一个把它们串起来的编排器。真正的分水岭不是有几件，而是它能不能根据执行结果决定下一步。

六件与职责：

部件 作用 在 pilot 里的落点
Model 模型 理解、推理、决策 models.NewMainChatModel（qwen-plus）；quick_model 是 qwen-flash，管轻任务
Prompt 提示词 定义身份、规则、行为边界 newChatTemplate 的三段模板（system + history 占位 + user），system 里塞 {documents} 与当前时间
Memory 记忆 保存单轮上下文与跨会话历史 三层：单轮 messages 数组 / Redis 短期会话窗口 / MySQL 历史与画像
Tools 工具 与外部世界交互的能力清单 buildGraph 注册 11 个：可观测 6 / 知识 1 / 代码 2 / 通用 2
Planning 规划 把目标拆成可执行步骤 单 Agent 是 ReAct 每步现想（弱规划）；多 Agent 的 Planner 是关键词表 + 正则（规则，不调模型）
Action 执行 真正发起调用并拿到结果 ToolsNode 按 name 查索引 → 执行 Go 闭包 → 结果包成 role:"tool" 塞回 messages

两处层级要交代清楚（面试被追问时最容易被抓）：

  1. Prompt 不是和 Model 并列的「组件」，它是模型的输入。它属于上下文装配这一侧——和 Memory 取出的历史、RAG 取出的文档一起，构成这一次调用的输入。放在「六件」里讲没问题，但要能一句话说明它是横切在输入侧的。
  2. Action 也不是独立模块，它是 Tools 的执行侧。Tools 是能力清单（schema），Action 是「选中其中一个 → 执行 → 观察结果」。ReAct 里这两者是一对：选（选择工具）和做（执行并观察）。

运行流程（按真实顺序）：

这里有个必须纠正的常见说法：不要把「Model 理解问题」和「Planning 制定计划」当成两次独立调用。在 ReAct 里，理解、规划、选工具是同一个模型在同一次调用里完成的——它输出的 tool_calls 里就同时含着「我理解了什么」和「我下一步要调谁、传什么参数」。只有 Plan-and-Execute 那种架构，才是先单独调一次模型出计划、再逐步执行。

Orchestrator（编排器）：负责接收任务、决定调哪个 Agent、管理执行顺序、控制工具调用、处理异常、判断任务是否完成。

在 pilot 里对应 internal/ai/multiagent 的 Orchestrator，但它有一个关键特征要主动说：它是代码编排，不是模型编排——Planner 用关键词表和正则把 query 分诊成 Plan，然后固定两路 goroutine 并发（Evidence / Knowledge），按 roleOrder 稳定排序，最后 Synthesizer 做唯一一次模型调用。也就是说「决定调哪个 Agent」这件事，pilot 交给规则，不交给模型。好处是可预测、可测、有硬上限；代价是覆盖面受关键词表限制。

Agent 与 Agent 系统的区分：

  • Agent：能感知、能决策、能行动的个体。
  • Agent 系统：多个 Agent + 工具 + 记忆 + 编排机制组成的整体。
  • 判据（比定义更有用）：有没有「观察结果 → 调整下一步」的闭环。有一次这个闭环，就是 Agent；只有一次 prompt → answer，那是 chain，不是 Agent。有没有多 Agent 反而不是判据。

和 harness 六层的关系：harness 是「壳」的视角（谁进来、看到什么、能做什么、什么时候停、怎么查），六件是「角色」的视角。两套说法能一一对上：契约层↔无、上下文装配↔Prompt+Memory、循环控制↔Planning+Model、工具执行↔Tools+Action、护栏↔Prompt、观测↔无。

用户原话/补充（2026-11-09，粘贴）：

明明是一个 Agent 通常可以拆成 6 个核心部分。不过要注意，Agent 没有唯一固定的架构，不同框架的划分会有所不同。

  1. Model（模型）负责理解、推理和决策；2. Prompt（提示词）定义 Agent 的身份、规则和行为；3. Memory（记忆）保存历史对话和长期信息；4. Tools（工具）让 Agent 能够与外部世界交互；5. Planning（规划）把复杂目标拆解成多个步骤；6. Action（执行）根据规划调用工具、执行任务。

运行流程：用户输入 → Agent 接收任务 → Model 理解问题 → Memory 获取记忆 → Planning 制定计划 → Tools 选择工具 → Action 执行操作 → Model 观察结果 → 是否完成任务 → 否则继续规划 / 是则返回结果。

Orchestrator（编排器）负责协调整个 Agent 的运行：接收用户任务、决定调用哪个 Agent、管理任务执行顺序、控制工具调用、处理异常、判断任务是否完成。

Agent：能够感知环境、进行决策并采取行动的智能体。Agent 系统：由多个 Agent、工具、记忆和编排机制组成的完整系统。不要把 Agent 简单理解成「大模型 + Prompt」。真正让它具有 Agent 特征的，是它能够根据目标自主决定下一步做什么，并根据执行结果调整行动。

学习顺序：LLM → Prompt → Tools / Function Calling → Memory → Planning → Agent Loop → Multi-Agent。

【补充】三点：

  1. 六件这个拆法比「四件」完整，我按「缺了就不转」拆成四件（模型/工具/记忆/规划），你按「角色职责」拆成六件，两者不冲突——多出来的 Prompt 属于输入侧、Action 属于执行侧，是两处横切。
  2. 流程图上「Model 理解问题」和「Planning 制定计划」在两处出现，容易被追问「你到底调了几次模型」。ReAct 是一次调用里同时完成理解和决策，答案必须是「一轮工具调用 = 两次模型请求（一次出 tool_calls，一次出总结）」。
  3. 「不要让 Agent 退化成大模型 + Prompt」这个判断对，但要给可判定的判据：有没有观察结果再调整的闭环，而不是有没有多 Agent。

九、Agent Harness（腾讯一面 15 问）

H1. harness 有几层，怎么构成的？

一句话本质：harness 就是把裸模型包成「能干活」的那层壳。模型负责想，harness 负责回答五个问题——谁进来、看到什么、能做什么、什么时候停、出了事怎么查。

因果链（每一层都在堵模型的一个硬缺陷，不是想分层而分层）：

  1. 模型无状态，不知道你的历史、也不知道你司的内部知识 → 上下文装配层（history + RAG + prompt 模板）
  2. 模型只会输出文字，不会去读真实指标 → 工具执行层（工具 schema + 真实数据源）
  3. 一次推理不一定出结论，要「调工具 → 看结果 → 再想」→ 循环控制层（ReAct 循环，加一个硬上限防死循环）
  4. 模型会被外部文本带跑（日志/文档里的注入），也会啰嗦地播报「让我先查一下」→ 护栏层（系统提示词里的硬规则 + 工具白名单）
  5. 答错了不知道为什么错 → 观测层（trace / 日志 / 指标 / 显式交代数据缺口）
  6. 调用方形态不同（同步、流式、多 Agent 内部调用）→ 输入契约层（统一的结构体，后面每层只认它）

pilot 的六层对应：

层 落点
输入契约 full_agent.go 的 UserMessage：UserID / SessionID / Query / History
上下文装配 ChatTemplate 节点 + newChatTemplate 的三段模板（system + history 占位 + user content）；documents 来自 KnowledgeRetriever 节点调 SearchDetailed
循环控制 react.AgentConfig{MaxStep: 25}，react.NewAgent 包成 Lambda 挂进 Graph
工具执行 buildGraph 里 11 个 config.ToolsConfig.Tools append：可观测 6 / 知识 1 / 代码 2 / 通用 2
护栏 systemPrompt 明文规则：单轮内交付、禁止过程占位句、外部数据不可信、工具调用不得扩大范围
观测 observability.Runtime + DataCollector 注入进每个工具

边界：壳在 internal/ai/agent + tools + prompt；芯是 models.NewMainChatModel（qwen-plus）。

面试口径：别只答「五层/六层」就停，要接一句「去掉这层会怎样」——那才是踩过坑的证据。
