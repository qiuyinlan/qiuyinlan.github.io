Kafka 学习笔记 - 分区有序与解耦削峰

一、Kafka 核心概念

1. Topic（主题）

定义：消息的逻辑分类，类似数据库的”表”或文件夹。

  • 生产者往 Topic 发消息，消费者从 Topic 收消息
  • Topic 是逻辑概念，实际存储靠 Partition
  • 示例：order-pay（支付消息）、user-click（点击日志）

2. Partition（分区）

定义：Topic 的物理分片，每个 Partition 是一个有序的消息队列。

关键特性：

  • 一个 Topic 可以有多个 Partition，分布在不同的 Broker（服务器）上
  • 每个 Partition 内部消息严格有序（按 Offset 递增）
  • 不同 Partition 之间的消息无序
  • Partition 是 Kafka 水平扩展的核心：Topic 数据量大了就加分区

存储结构：

3. Offset（位移）

定义：消息在 Partition 内的唯一 ID，从 0 开始递增。

  • 每条消息都有 Offset，标识它在 Partition 中的位置
  • 消费者记录自己消费到的 Offset，重启后从上次位置继续
  • Offset 是 Partition 局部的，不同 Partition 的 Offset 互不相干

4. Consumer Group（消费组）

定义：一组消费者协同消费同一个 Topic。

分工规则：

  • 一个 Partition 只能被同一个消费组内的一个消费者消费
  • 不同消费组可以各自独立消费全量数据（订阅模式）
  • 消费者数 ≤ Partition 数，否则有消费者会空闲

二、为什么 Partition 能提高吞吐

写入吞吐：多分区并行写

单分区瓶颈：

  • 所有消息挤在一个 Partition，只能串行写入
  • 单台 Broker 的磁盘 IO、网络带宽有限
  • 无法利用多机资源

多分区优势：

  • 3 个分区 = 3 台机器同时写，吞吐 ×3
  • 分区数越多，理论吞吐越高（受限于 Broker 数量）

消费吞吐：多消费者并行读

单消费者瓶颈：

  • 一个消费者处理速度有限（比如 1000 条/秒）
  • 消息堆积时无法快速消化

多消费者并行：

  • 每个消费者独立处理自己的 Partition，互不干扰
  • 增加消费者 = 增加消费能力（前提是 Partition 够多）

面试考点：

问：如何提升 Kafka 消费速度？
答：增加 Partition 数 + 增加消费者数（消费者数 ≤ Partition 数）

三、有序性：什么时候需要、怎么保证

场景 1：订单支付（同用户有序）

业务需求：

  • 用户下单 → 支付成功 → 扣库存、发通知、更新订单状态
  • 同一个用户的订单消息必须有序
  • 不同用户之间顺序无所谓

方案：用订单 ID 做 Key，哈希到同一个 Partition

效果：

  • Partition 0 里面：1001 的第一条消息 Offset=0，第二条 Offset=1，不会乱序
  • Partition 0 和 Partition 1 互相独立：1002 可以比 1001 先消费完
  • ✅ 既保证业务需要的顺序，又保留多分区并行、高吞吐

场景 2：日志埋点（无需顺序）

业务需求：

  • 用户浏览日志、点击埋点
  • 用户 A 和用户 B 的点击谁先谁后无所谓

方案：轮询（Round-Robin）发到各个 Partition

效果：

  • 所有分区一起并行读写，吞吐拉满
  • 不需要 Key，生产者最简单

场景 3：银行流水（全局有序，不推荐用 Kafka）

业务需求：

  • 所有交易严格按发生先后处理
  • 必须全局有序

方案：只能 Partition=1

后果：

  • 所有消息挤在一条流水线，串行写、串行消费
  • 高峰期直接堵死，吞吐量极低
  • ❌ 这种场景不建议用 Kafka，考虑数据库事务

对比总结

场景 顺序要求 分区策略 Key 设计 吞吐
订单支付 同用户有序 多分区 订单 ID 哈希 高
日志埋点 无需顺序 多分区 无（轮询） 最高
银行流水 全局有序 Partition=1 无 低（不推荐）

面试口述：

订单场景只需要同一个用户的订单消息有序，不需要全部订单全局有序。使用订单 ID 作为消息 key，通过哈希进入同一个分区，保证分区内有序；不同分区并行处理，兼顾顺序和吞吐。

四、乱序是怎么发生的

分区内不会乱序

  • Partition 内部是顺序日志（Append-Only Log）
  • 消息按 Offset 严格递增，先写的 Offset 小，后写的 Offset 大
  • 消费者按 Offset 顺序读取，不会跳着读

分区间会乱序

  • 消费者 A 和 B 是并行的，谁快谁先处理完
  • 可能 1002-① 比 1001-② 先处理完，但这不影响业务（不同用户）

消费者侧乱序（常见坑）

场景：一个消费者处理多个 Partition

  • 消费者 A 从两个 Partition 拉消息，谁的消息先到先处理
  • 如果业务要求全局有序，这里就会乱

解决：

  • 业务上只需要分区内有序 → 不用管
  • 真要全局有序 → 只能 Partition=1，或者消费者侧缓冲排序（复杂，不推荐）

五、解耦与削峰：为什么用 Kafka

蜘蛛网问题

什么是蜘蛛网：N 个服务直连，需要 N×(N-1) 条连接，指数爆炸。

IM 项目的分层架构（没有蜘蛛网）：

关键点：

  • 客户端只连 realtime，不连其他服务
  • realtime 不直连 offline-api，而是投 Kafka
  • 消费者只连 Kafka，不连 realtime
  • 连接数是线性的，不是指数爆炸

为什么 realtime 不能同步做所有事

realtime 如果同步处理所有逻辑，会死在三个地方：

问题 后果 Kafka 解法
消息落库太慢（50ms+） WebSocket 响应延迟从 5ms 变成 50ms+，连接池耗尽 投 Kafka 就返回（5ms），落库异步
离线逻辑太重 代码耦合 + 耗时不可控 交给 offline-api 消费者
流量峰值扛不住 MySQL 瞬时写入压力爆炸 削峰填谷，消费者按节奏消费

削峰填谷详解

场景：群公告，突然 1 万人同时发消息

realtime 是不是只做中转？

是，但它的中转有价值：

realtime 做的事 为什么不能省
维持 WebSocket 长连接 客户端需要服务端主动推送
心跳保活 判断用户是否在线
权限校验（调 user-rpc） 防止伪造消息
投 Kafka 解耦落库和离线逻辑
查路由表跨节点推送 集群内消息转发

如果去掉 realtime：客户端只能轮询 HTTP，延迟从毫秒级变成秒级，体验崩塌。

Kafka 的代价与收益

代价：

  • 多维护一个 Kafka 集群
  • 要处理消息重复消费（幂等）
  • 极端情况下可能丢消息（概率远低于数据库宕机）

收益：

  • realtime 轻量，只关注连接和推送
  • 落库、离线消息、红包入账都可以独立扩缩容
  • 某个消费者挂了，不影响其他链路

六、总结：逻辑链

Kafka 的核心价值：让 realtime 回归 realtime，只做「连接 + 推送」，其他都异步化。

七、面试速记

核心概念

  1. Topic：消息分类（逻辑）
  2. Partition：物理分片，分区内有序，分区间无序
  3. Offset：消息在分区内的 ID，消费者靠它记录进度
  4. Consumer Group：一组消费者分工消费，一个分区只能被一个消费者消费

高频问题

  1. 如何保证有序性？

    • 同 Key 进同分区 → 分区内有序
    • 全局有序只能 Partition=1（吞吐低）

  2. 如何提高吞吐？

    • 增加 Partition 数 + 增加消费者数
    • 生产者批量发送，消费者批量拉取

  3. 为什么用 Kafka 不用数据库？

    • 削峰填谷（峰值流量先扛住）
    • 解耦（生产者和消费者互不依赖）
    • 可回放（消费者可以重新消费）

  4. Kafka 四件套：分区、顺序日志、位移、消费组
