Pilot 记忆系统设计：Redis 工作记忆与 MySQL 历史档案的冷热分层

一句话本质

记忆系统要解决的核心矛盾是：Agent 推理需要「快且高频」的上下文，用户查历史需要「完整且持久」的记录——这两者无法用一套存储同时满足。

所以 Pilot 用了冷热分层：

  • Redis 存工作记忆：每次聊天必走，低延迟，只保留最近 20 轮，TTL 24h 过期
  • MySQL 存历史档案：聊天后异步写入，持久化，可追溯，可分页查询

最容易误解的事实：Agent 推理时只查 Redis，不是「先查 MySQL 再回退 Redis」。后者只用于用户主动查历史的接口，且这个设计本身有争议。

为什么需要两套存储？

访问模式的根本冲突

维度 Agent 取上下文 用户查历史
频率 每次聊天都读（高频） 偶尔点开看（低频）
延迟要求 必须快（拼进 prompt 要等） 可接受稍慢（5-20ms 无感）
数据范围 只要最近 N 轮 要完整历史
持久化要求 可接受过期（TTL） 必须持久化
并发 10w+ QPS 几千 QPS

结论：如果用 MySQL 同时扛这两类请求：

  • 每次聊天多花 10-20ms（不划算）
  • 并发上来后 MySQL 压力巨大
  • 历史查询会跟推理抢资源

如果用 Redis 同时扛这两类请求：

  • 过期后历史就丢了（用户隔天查不到）
  • 无法做复杂查询（分页、检索、审计）

所以必须冷热分层。

数据流向：三次写入，两次读取

写入链路（聊天时）

关键细节：

同步聊天 vs 流式聊天的写入差异：

类型 Redis 写入时机 MySQL 写入时机
同步聊天 Agent 一次性写完 user + assistant 控制器拿到完整回答后写入
流式聊天 Agent 先写 user，流结束后补写 assistant 控制器汇总 fullContent 后写入

为什么流式聊天要分开写：

  • 流式过程中只知道增量 chunk
  • 如果每收到一个 chunk 就写一次 Redis，会把 assistant 消息切成碎片
  • 所以先写 user，等流结束后汇总完整内容再补写 assistant

为什么 MySQL 是「最佳努力」：

原因：主响应成功比持久化更重要，数据库瞬时抖动不该影响用户拿到 AI 回答。

读取链路（查历史）

场景 1：Agent 取上下文（每次聊天必走）

只查 Redis，不查 MySQL——因为：

  • 只需要最近 20 轮
  • 每次聊天都会更新 Redis，TTL 被刷新，不会过期
  • 1ms 延迟 vs 20ms 延迟，拼进 prompt 要等

场景 2：用户主动查历史（GetHistory 接口）

为什么这个顺序（八股文档的解释）：

  • MySQL 是长期、可靠、可追溯的来源
  • Redis 会过期（TTL 默认 24h），用户隔天查可能已经空了
  • 用户刷新页面后仍应看到历史，不能因为 Redis 过期就清空

但这个设计有争议（后面讲）。

清理链路（删会话）

为什么都要删：

  • 只删 Redis → 用户查历史时仍从 MySQL 读出，不符合「清空」预期
  • 只删 MySQL → Redis 里的上下文还会影响后续 AI 推理

Redis 设计细节

Key 设计

为什么这样设计：

  • 按用户和会话隔离上下文，不同 session 不会相互污染
  • 摘要单独存，用于长对话压缩（预留能力）

滑动窗口（防上下文爆炸）

逻辑：

为什么这么做：

  • 模型只需要最近 N 轮对话，不是无限增长
  • 避免单 key 过大（Redis 大 key 问题）
  • 默认 20 条是保守值，兼顾上下文完整性和成本

分片设计（代码预留，默认不触发）

设计：

实际情况：

  • max_messages = 20（滑动窗口上限）
  • chunk_size = 100（分片阈值）
  • 因为先裁剪再判断，消息永远不会超过 20 条，所以分片逻辑默认不生效

这是「代码准备好了但参数没启用」的设计，属于预留能力。如果未来需要支持长对话（比如 500 轮），只需调大 max_messages，分片逻辑自动生效。

争议点：GetHistory 为什么先查 MySQL？

八股文档的解释

为了数据可靠性：

  • Redis 有 TTL（默认 24h 过期）
  • 用户隔天查历史，Redis 可能已经空了
  • MySQL 是持久化的，即使 Redis 过期了，历史还能找回来

但这个设计有问题

性能对比：

操作 Redis MySQL
读取延迟 ~1ms（内存） ~5-20ms（磁盘 + 索引）
并发能力 10w+ QPS 几千 QPS

场景分析：

场景 1：多轮对话进行中

  • 用户：「帮我查告警」
  • 用户：「那日志呢？」
  • 用户：「再看看指标」

这个时候，Agent 需要的是当前会话上下文：

  • 每次聊天都会更新 Redis
  • TTL 被不断刷新，不会过期
  • 应该直接从 Redis 取（事实上 FullPilotAgent 就是这么做的）

场景 2：用户主动查历史

  • 用户隔天打开界面，点「查看历史对话」
  • Redis 可能已经过期了
  • 应该从 MySQL 取

问题出在哪？

GetHistory() 这个接口把两个场景混在一起了。

更合理的设计应该是：

  1. Agent 取上下文 → 只查 Redis（快，且不会过期）
  2. 用户查历史 → 只查 MySQL（完整，可分页）
  3. 不需要「先查 MySQL 再回退 Redis」这种混合逻辑

面试时怎么答？

「这个设计有争议。从性能角度应该先查 Redis，但项目里为了数据可靠性选了 MySQL 优先。我个人认为更好的做法是把两个场景分开：Agent 取上下文走 Redis，用户查历史走 MySQL，不需要混合逻辑。」

能说出这个权衡，比死记「先查 MySQL」更有价值。

故障场景

故障 影响
Redis 挂了 Agent 读不到短期历史 → 聊天链路失败
MySQL 挂了 启动时可能失败；运行时历史写入失败但聊天仍可用（最佳努力）
Redis 过期 用户查历史时回退 MySQL，不影响长期数据

关键认知：Redis 是主链路依赖，MySQL 是旁路依赖——主响应成功比持久化更重要。

对比总表

维度 Redis（短期记忆） MySQL（长期历史）
数据类型 List（有序对话） 表（结构化记录）
Key/表 pilot:memory:short:{userID}:{sessionID} chat_history
访问频率 每次聊天都读 查历史/审计时才读
延迟要求 低延迟（ms 级） 可接受稍高
持久化 可接受过期（TTL 默认 24h） 必须持久化
清理方式 TTL 自动 + 滑动窗口 手动 DELETE
失败影响 聊天链路直接失败 仅影响历史查询，主链路仍可用

一句话收口

Redis 是 Agent 的「工作记忆」（每次聊天必用，快、热、会忘），MySQL 是用户的「历史档案」（查的时候才有用，稳、冷、可追溯）—— 各司其职，故障时互不拖垮。
