从浮点数到向量检索：ES、BM25 与 Agent 评测

零、主干流程速查（先看这个）

流程 A：一份文档入库（写）

代码：knowledge_controller.go → knowledge_retriever.go → elasticsearch.go（详见 Q5、Q11）

流程 B：一次检索（读）

LLM 从头到尾没看见过向量。（详见 Q13）

流程 C：一次评估（评测）

前置条件：工具调用必须落盘（见JSON、JSONL 与 Function Calling 的 Q10）。（详见 Q14–Q17）

一、浮点数

Q1. 浮点数是什么？

用「科学计数法的二进制版」表示小数：±1.xxxx × 2^e，由符号位、尾数、指数三部分组成。

float64 是 1 位符号 + 11 位指数 + 52 位尾数。小数点位置「浮动」，所以范围大。

两个必答的坑：

  • 不精确：0.1 在二进制是无限循环小数，只能截断，所以 0.1+0.2 != 0.3。金额要用整数（分）或 decimal。
  • 精度丢失：大数吃小数（1e16+1 == 1e16），比较要设误差，不能 ==。

一句话：浮点是「近似表示连续小数」的方案，快、范围大、但不精确，所以不能算钱。

Q2. 向量模型也返回浮点数，那不就不精确了？

两层「精确」被混在一起了。

  • 浮点的不精确是绝对误差（0.1 存成 0.1000000015）。但 embedding 从来不关心单个分量的绝对值，只关心向量之间的相对关系（余弦、排序）。
  • 误差随机分布，算相似度时大量分量互相抵消；float32 有 7 位有效数字，对「判断语义像不像」是过剩的。
  • 模型前向全是浮点乘加，答案本来就是浮点算出来的，不存在「精确答案被污染」。

更进一步：把向量量化成 int8，检索召回率通常只掉 1~2 个点。因为 top-k 要的是排序大体正确，不是分数分毫不差。

对比记忆：算钱用整数，算向量用浮点。前者怕绝对误差，后者只要相对顺序。

Q3. 内容一样、名字不一样，会算两遍吗？

会。embedding 只取决于 token 序列，跟文件名、标题、路径毫无关系。同内容不同名 → 两个逐位相同的向量 → 索引里两条记录。

两个后果：

  • 检索 top-k 返回重复内容，白占 context，还挤掉其他相关内容
  • 灌库成本翻倍

正确做法：

  • 灌库前对 chunk 文本做内容哈希当主键，命中就跳过
  • 文件名/来源路径只作 metadata，不参与去重
  • 是 chunk 级去重，不是文档级
  • 哈希要在文本清洗之后算，否则脏版/净版会被当成两份
  • 近似重复（改两行）哈希失效，要 SimHash / MinHash

即使标题内容完全相同，向量也已经调用完 API 了，最后只是被 ES 用同 ID 覆盖。只防住了索引重复，没防住成本重复。

Q5. 改成了什么样？

三件事：

  1. generateDocID(title, content) → generateContentID(content)，只哈希内容；新增 normalizeContent() 把连续空白（含换行、CRLF、行尾空格）折叠成一个空格，避免排版差异造成伪重复。
  2. IndexDocument 里去重前置到 embedding 之前：先算 ID → elasticsearch.DocumentExists() → 命中直接 return，embedding 调用次数为 0。
  3. BatchIndexDocuments 用 seen map 去批内重复 + 逐个 exists 过滤 → 剩下的一次性交给 EmbedBatch()，避免一条一个请求。

配套新增 pkg/elasticsearch/elasticsearch.go 的 DocumentExists(ctx, index, docID)，404 视为「不存在」而非错误。

边界： 显式传 ID 时保留覆盖更新语义（只对内容生成式 ID 做「存在即跳过」）；近似重复识别不了。

面试口径：不是强业务主键设计，而是「按内容幂等 + 成本前置拦截」。

三、ES 到底怎么存的

Q6. ES 就是一个无限存 JSON 的文档库吗？

大体对，但四个限定：

  1. 存储单位是 document（JSON），归在 index 里，index 再切成 shard。
  2. 落盘不是一个大文件：每个 shard 是一个 Lucene 目录，里面是若干 segment，每个 segment 又一堆文件（.tim/.tip 词典、.doc 倒排、.pos 位置、.fdt 原始 _source、.dvd 列存），另有 translog 保证未 refresh 时的持久化。
  3. 不是无限：单分片建议几十 GB 内，总量靠加分片和节点扩；_source 可关。
  4. 不是完全 schema-free：mapping 定型后写错类型要 reindex。

核心机制：segment 不可变。

  • 新增 → 写新 segment
  • 删除 → 只在 .del 打标记
  • 更新 → 标删旧的 + 写新的
  • 定期 merge 合并，物理清理

后果：同 ID 覆盖写入，底层也是「标删 + 新增 segment」，物理先多了再靠 merge 收拾。所以去重要前置到 embedding 之前，不能指望 ES 帮你省。

Q7. MySQL 背后是一个文件吗？

也不是。InnoDB 是 ibdata1 / xxx.ibd 表空间文件，内部切成 16KB page，按 B+Tree 组织；另有 redo log、undo、binlog。

关键对比：

  • MySQL：一棵可原地修改的 B+Tree，靠 redo/undo 保证正确性，适合事务型随机读写
  • ES：一堆不可变倒排 segment 不断追加和合并，适合写一次、查多次；代价是写放大

Q8. 为什么 40G 云盘一编译就挂？盘不是挺大吗？

瓶颈是性能配额，不是空间。

  • 云盘的 IOPS/BPS 配额按容量线性给，40G 在最低档（rotational=1，内核按机械盘对待，本质是网络存储块设备）
  • go build 是几十万个小文件随机写（每个依赖包一个 .a、一堆 .o、索引文件），吃 IOPS 不吃顺序带宽
  • 1.7G 内存小，page cache 攒不住脏页，频繁回写，写放大更明显
  • 打满配额 → StoragePerformanceReachLimit → 云盘限速惩罚 → 越写越慢，雪崩

结论：不是「永远不能编」，是「不能裸编」。 现实做法是本地编译 / CI 编译；真要在这台机器上编，必须 cgroup io.max 限速 + 后台跑 + 只编单包，代价十几到几十分钟。

项目规则已固化：AI 不在服务器上跑 go build / go vet / go test，见 AGENTS.md「编译验证流程」。

四、倒排索引与 BM25

Q9. 什么是倒排索引？

正排 = 文档 → 词；倒排 = 词 → 文档。

例子：

  • 文档1：redis 连接超时
  • 文档2：mysql 连接池
  • 文档3：redis 内存溢出

倒排表：

搜 redis 直接查表拿 [1,3]，顺序扫描变成一次查表。多词查询就是求交集。

Lucene 里的对应文件：

  • .tim / .tip：词典（FST 压缩，快速判断词是否存在）
  • .doc：倒排表（文档 ID 列表 + 跳表，方便求交）
  • .pos：位置信息（支持短语搜索）

前置步骤是分词：中文要先切词，再小写、去停用词。切错了就永远搜不出来。

Q10. BM25 一定要配倒排索引吗？

不是必须捆绑，但工程上总是绑在一起——因为刚好互补。

BM25 是打分函数，倒排索引是存储结构，不在一个层面。

BM25 需要四样统计量，而倒排索引全都有：

  • tf：词在本文档出现次数 → posting 里带
  • df：多少文档含此词 → 词典里的 docFreq
  • 文档长度 → norms（.nvd/.nvm）
  • 全局统计 → segment 的 .stats

但两边都能拆开：

  • 倒排索引可以不配 BM25：早年 Lucene 默认 TF-IDF，ES 5.0 后才换 BM25；也能只做布尔检索；也能把 BM25 当特征喂 LTR
  • BM25 也能不配倒排：稀疏向量方案（SPLADE）走向量检索；小规模内存直算

为什么实际总绑一起：BM25 和倒排的强项是同一件事——精确词项匹配。搜报错码、专有名词、版本号，BM25 又快又准；换个说法问就废，那部分交给向量。这就是 Pilot 做两路独立召回 + RRF 融合的原因。

两个面试坑：

  1. 分片统计问题：BM25 的 df 是分片内统计，多分片时同一文档分数不可比，跨分片排序失真。解法 search_type=dfs_query_then_fetch（多一轮往返）。
  2. 参数可调：k1=1.2 控制词频饱和，b=0.75 控制文档长度惩罚，可按字段配 similarity。

一句话：BM25 是公式，倒排索引是数据源，ES 焊死的原因是最优搭配，不是技术依赖。

五、向量怎么存、怎么检索（走代码）

Q11. 向量是哪一步存的？其他信息哪一步传进去的？

最容易误解的事实：全程只有一次写请求，向量和文本是一起进去的。

第 1 步 knowledge_controller.go — 构造文档，此时没有向量

第 2 步 knowledge_retriever.go — 算内容哈希 ID + DocumentExists 查重，命中直接 return（连模型都不调）

第 3 步 knowledge_retriever.go — 唯一一次调 embedding 模型，向量在这里产生

第 4 步 knowledge_retriever.go — 向量挂回同一个 struct

第 5 步 knowledge_retriever.go — 整个 doc 指针交给 ES

第 6 步 pkg/elasticsearch/elasticsearch.go — 序列化成一个 JSON body

body 里同时有 title/content/category/tags/vector/created_at/updated_at。

第 7 步 pkg/elasticsearch/elasticsearch.go — 一次 HTTP PUT 落盘

ES 拿到后按 mapping 拆（knowledge_retriever.go）：

  • title / content → text + standard 分词器 → 分词、建倒排
  • category / tags → keyword → 不分词，精确匹配索引
  • vector → dense_vector，dims=1024，similarity=cosine → 存向量数据，不建倒排
  • 所有字段原始值 → 全部进 _source

所以同一份 content 在磁盘上存在两处：倒排表里（切碎成词）负责「找到它」，_source 里（完整原文）负责「还给你」。

Q12. 只发向量，模型怎么倒排？文档内容在哪？

方向搞反了：不是把向量发给模型，是模型吐出向量。 向量是结果，不是输入。

文档内容就在同一个 document 里，和向量是不同字段：

倒排只建在文本上，跟向量没关系。 双轨结构：text 字段建倒排，dense_vector 存向量，互不相干。

向量检索不走倒排，是算数。 Pilot 用的是暴力扫描：

O(N) 全量算余弦再排序。没有倒排、没有图结构。ES 8 也支持 knn 字段（HNSW 近似最近邻），百万级以上才需要。

Q13. 完整检索链路

用户问 Redis 连不上怎么办：

  1. BM25 路：分词 → 查倒排表求交 → BM25 打分 → top-k（只碰文本）
  2. 向量路：query → embedding → 和库里所有向量算余弦 → top-k（只碰浮点）
  3. 融合：RRF 合并重排、去重（recall.go 的 fuseRRF，得分 Σ 1/(k+rank+1)，k=60）
  4. 喂 LLM：把命中文档的 content 原文拼进 prompt

LLM 从头到尾没看见过向量。 向量只在检索阶段当中间变量用了一次就被扔了。

向量是「找文档的钥匙」，内容是「最终给模型看的资料」。

六、Agent 评测

Q14. 怎么评价一个 Agent 的表现？

不能用一个分数，分三层：

第一层 单步质量（工具选择对不对） — 最好评，因为输入输出都结构化：工具选择准确率、参数正确率、无效调用率。

第二层 链路质量（多步走完没有） — 任务完成率、平均步数/冗余步数、失败可恢复率、循环检测。要评得有 golden trajectory 对照。

第三层 端到端质量 — 任务成功率、结论有没有证据支撑（Agent 特有，最怕编）、幻觉率、token 成本和 P95 延迟。

方法三条腿：

  • 离线评测集：固定问题 + 期望轨迹，改 prompt/换模型就回归跑，防「改 A 坏 B」
  • LLM as judge + 人工抽检：批量打分，再人工抽 10% 校准裁判
  • 线上埋点：步数、工具命中、耗时、token 全打点，覆盖离线集碰不到的长尾

落到 Pilot 要诚实划边界：

现有三层验证是 cmd/checkdeps（依赖连通性：Redis/ES/MySQL/Prometheus/Jaeger/DashScope Key/日志索引）、cmd/e2echeck（真跑全链路：上传→检索→真实聊天→查历史→校验各存储有数据）、单测（输入规范化/SSE 格式化/时间戳解析/ES 结果解析/中间件连通）。

但这三层解决的是「链路通不通、功能有没有坏」，属于可观测性和集成正确性，不等于「回答质量好不好」。

缺的是：golden 评测集 + 工具调用准确率统计 + 结论证据溯源。

加分点： 面试官想听的不是「我调了很多 Prompt 所以效果好」，而是（1）知道要拆过程指标和结果指标（2）意识到「链路跑通」≠「答得对」（3）主动说出自己项目的边界，不把 e2e 包装成效果评测。

Q15. 「自动比对」具体怎么做？举个例子

前提：工具调用本身就是结构化的（tool 是枚举，args 是 JSON），所以能机械比对。

① 写评测样本（golden case）

只写工具集合 + 关键参数，不写死完整轨迹（写太死会把正确变体判错）。

② 抽出实际调用

③ 比对规则要分档，不能一把 ==

  • tool 名：精确
  • 枚举参数（level: error）：精确
  • 时间窗口：容忍（15m 和 10m 都算对）
  • 服务名/实例 ID：精确或包含
  • 数值阈值：浮点容差 |a-b| < 0.01
  • 自由文本（关键词）：正则或命中率

④ 算分

整体 pass：toolScore == 1 && paramScore >= 0.8。

⑤ 三个例子看差别

  • 期望 query_logs(service=payment, window=15m)，实际 window=10m → 时间走容忍 → pass
  • 实际 service=order → 服务名错，硬伤 → fail
  • 实际只调了 search_knowledge → 工具召回 0/2 → 0 分（典型的路由错了）

⑥ 批量跑 + 回归：输出工具选择准确率、参数完全正确率、端到端 pass 率、失败样本清单。每次改 prompt / 换模型重跑，分数掉了就说明改坏了——和单测一个道理，只是被测对象从函数变成 Agent。

两个工程细节：

  1. 别用字符串比 JSON：{"a":1,"b":2} 和 {"b":2,"a":1} 语义相同，必须解析成 map 逐 key 比
  2. 期望值要留「或」：查告警调 query_alerts 对，调 query_metrics + 自己判阈值也算合理。写死会天天误报，最后没人看

一句话：自动比对 = 把工具调用当 API 断言来测，工具名精确、参数分类型给容差、集合比较不看顺序。

Q16. 这是专门的评测脚本做的吗？

通常是，但不一定。三种形态：

形态一：独立 cmd/eval（最推荐）

Pilot 已有 cmd/checkdeps、cmd/e2echeck 的先例，同一个路子，不引入新依赖。

形态二：塞进 go test — 好处是顺手跑，坏处致命：Agent 评测要调真模型，慢、要钱、非确定性。放进 CI 结果就是天天红然后被 -short 跳过。最多打 //go:build eval 单独跑。

形态三：现成平台 — Promptfoo（最轻，yaml 声明用例）、Langfuse/LangSmith（带 trace 回放）、Ragas/DeepEval（偏 RAG 质量）、OpenAI Evals。Go 生态基本没有好用的，Eino 也不带，所以 Go 项目现实做法是自己写 scorer + 接 LLM judge。

真正重要的不是「有没有脚本」，而是三件事：

  • 数据集版本化：进 git，改了就 diff 得出来。不冻住数据集，历史分数没法比
  • 跑批可复现：记录模型快照名、prompt 版本、temperature、随机种子。否则今天 70 明天 65，分不清是代码坏了还是模型抖了
  • 结果留档可对比：每次出报告存下来看曲线，而不是「我印象中变好了」

Pilot 的诚实答法： 目前没有独立 Agent 评测脚本，验证体系是「连通性 + e2e + 单测」，解决「跑不跑得通」，不解决「答得对不对」。追问怎么加，就答形态一那套。知道缺什么、也知道第一步落在哪，比硬说「我们有评测体系」强。

Q17. 工具调用的 JSON 是执行时本来就有吗？方便后续评测吗？

协议里天然有，但 Pilot 没存下来。这两件事要分开说。

第一层 模型协议（OpenAI function calling）：

坑：arguments 是 JSON 字符串，不是对象，评测要再 json.Unmarshal 一次。

第二层 ReAct 循环：Eino 把 tool_calls 和执行结果（role:"tool" + tool_call_id）拼回消息列表喂下一轮（full_agent.go 挂 ToolCallingModel）。这些 tool 消息只活在这次的内存里，循环结束就没了。

第三层 持久化：Pilot 根本没落盘（关键）

pkg/types/types.go

只有 role 和 content，没有 tool_calls 字段。

chat_controller.go 落库：

只存「问了什么」「最终答了什么」，中间调了哪些工具、参数是什么、返回了什么全丢了。ES 里的运行日志是服务端 INFO/ERROR，不是结构化 trace。

所以要支持评测，得加一层 trace 落盘，最小形态是 JSONL（一行一条）：

实现：Eino ReAct 的 OnToolStart / OnToolEnd 钩子里抓 name + args + 延迟，写文件或独立 ES 索引。顺带好处不止评测——线上排查「用户说答错了」时能直接看这一步调了什么，比看最终回答有用得多。

面试答法： 分清「协议层」和「可观测层」。内存里有 ≠ 能事后审计。主动说出缺口（只能做到端到端，做不到工具级归因），比假装「天然能评测」强。

一句话：协议给了你 JSON，但没给你历史记录——要评测，得自己把 trace 写下来。

七、方法论沉淀（讲技术的正确姿势）

这次最大的教训不是知识点，是讲法。

讲「XX 是怎么工作的」，按真实执行顺序走代码：

  1. 分步编号，不按理论章节
  2. 每步给 文件名:行号 + 真实代码片段
  3. 每步说清「数据变成了什么 / 存在哪 / 谁调用了谁」
  4. 开头点破最容易误解的事实（如「只有一次请求」「向量是结果不是输入」）
  5. 结尾一句话收口

反面教材：第一次讲 ES 存向量时从倒排索引原理讲起，没落到代码，对方连问三轮（向量发给模型？文档存哪？哪一步存的？）才讲清——等于把对方的时间翻了三倍。
