HTTPS 的路由转发，发生在哪一层？

这是一道容易被一句话答完、但其实很容易被追问的题。

因为「路由转发」这四个字本身就有歧义：它既可以说「包怎么被送到这台机器」，也可以说「请求怎么被分到某个后端服务」。

拆成两层看，这题就清楚了。

一句话结论

HTTPS 加密不改变「包怎么走」，但把「按内容分流量」锁在了「必须先解密」之后。

第一层：三层转发，和加不加密完全无关

互联网是逐跳转发的，每个路由器只拆 IP 头看目的地址。

在它眼里，HTTPS 的包和 HTTP 的包没有任何区别 —— 都是 IP 包，都有目的 IP。

所以：网络层的路由转发在第三层完成，加密在这一层不产生任何影响。

第二层：四层负载均衡，只能看到 IP 和端口

要做多后端分流，四层负载均衡（LVS、Nginx stream 这类）看的是 IP + 端口。

它最多能判断「这是个 443 端口的连接」，再往里全是密文，什么都看不到。

所以四层能做的分流策略只有：按端口、按源 IP、按连接数。

第三层：七层路由，必须先解密

业务真正想要的是「按 path 路由」「按接口灰度」。

这些信息只存在于 HTTP 报文里，而报文在 TLS 记录里是密文。

所以要按 path 转发，就必须有人在中间解密 —— 这个点叫 TLS 终止（TLS termination），通常落在 Nginx、网关或者 K8s Ingress 上，证书也配在那里。

结论：七层路由永远发生在 TLS 解密之后，在没有解密的地方做不了。

唯一的例外：SNI 明文

前面讲过，客户端在 ClientHello 里会以明文上报域名（SNI），因为选证书发生在密钥协商之前。

那就意味着：不解密也能按域名分流。

Nginx 的 ssl_preread、四层网关的 SNI 分流都是这个思路：

这种模式叫 TLS passthrough：证书不放网关，放在后端服务上，网关只做 TCP 层的搬运。

它的天花板很清楚：只能到域名级，到不了 path。 因为 path 在密文里。

收口

  • 三层看 IP —— 和 HTTPS 无关
  • 四层看 IP + 端口 —— 只知道 443
  • 七层看 path —— 必须先 TLS 终止解密
  • SNI 明文让「不解密按域名转发」成为唯一例外

面试讲这题，先问一句「您说的是网络层的转发，还是七层的路由」，比直接背答案加分得多。
