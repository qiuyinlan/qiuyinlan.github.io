HTTPS 到底加密了什么？

很多人以为「HTTPS 就是把整个请求加密了」，也有人说「URL 不加密」。

这两种说法都不准确。真正好用的判断标准只有一条：

TLS 记录里的应用数据是密文，TLS 记录之外的一切都是明文。

下面按这条线一路拆。

一、哪些东西在密文里

把 HTTP 报文整块塞进 TLS 记录当载荷，加密之后才发出去。所以密文包含：

  • 请求行：方法、路径、查询串
  • 请求头：Host、Cookie、Authorization 全都在里面
  • 请求体
  • 响应状态码、响应头、响应体

注意是整个 HTTP 语义，没有「请求行不加密、请求头加密」这种切法。

二、哪些东西必然明文

不是「不想加密」，而是加密还没谈好，就得先用它。

  • IP 头：网络层的事，每一跳路由都要读它才知道往哪送。想藏 IP 只能再套一层（VPN / Tor）。
  • TCP 头：端口在里面。443 这个数字本身就把「你在走 HTTPS」暴露了。
  • TLS 记录头：类型、版本、长度，接收方得先读它才知道后面是握手还是数据。
  • ClientHello 里的 SNI：这是重点，后面单独讲。
  • TLS 1.2 的证书：证书消息里带域名和公钥，握手阶段是明文。

顺带说一句容易被忽略的差异：TLS 1.3 把 ServerHello 之后的所有握手消息（含证书）都加密了，明文只剩 SNI。所以「证书是明文」这个结论只对 TLS 1.2 成立，讲的时候要带上版本。

三、URL 到底加密没有

URL 拆开看：scheme://host:port/path?query

部分 加密 说明
path + query 加密 只存在于 HTTP 报文里，在 TLS 载荷中
host（域名） 报文里加密，但另有泄漏通道 SNI 明文、DNS 查询明文
port 明文 TCP 头里的 443
scheme 不适用 不在报文里，客户端自己知道

所以准确说法是：域名会暴露，但泄漏路径不是「从 URL 解出来」，而是 SNI 和 DNS。

这就是为什么 HTTPS 下 path 里的 token、订单号是安全的，而「你访问了哪个站」藏不住。

四、SNI 是什么，为什么必须明文

SNI = Server Name Indication，TLS 握手中 ClientHello 的一个扩展字段，内容就是域名。

它存在的理由很实在：一台服务器（一个 IP:443）上挂几十个网站，可是 TLS 握手发生在 HTTP 之前，服务器还没看到 Host 头，不知道该发哪张证书。所以客户端必须在握手第一步就报上域名。

而它必然明文的理由也一样实在：选证书发生在密钥协商完成之前。加密还没谈好，这个字段只能裸奔。

于是域名在传输中有两份副本：

  • Host 头里那份 —— 在报文里，加密的
  • SNI 里那份 —— 在握手阶段，明文的

抓包的人拿到的是第二份。

五、为什么必须对称 + 非对称搭配

两条路单独走都会死。

只用对称加密：一把钥匙既锁也开，速度快，但问题是这把钥匙怎么安全交给对方。网上直接传，被截获就全完了 —— 这叫密钥分发难题。

只用非对称加密：公钥加密只有私钥能解，像邮筒，谁都能投信只有主人能取。但它慢几个数量级，而且有个硬约束：

RSA 2048 一次最多只能加密约 245 字节。

物理上装不下业务数据，只能装一个密钥。

所以分工就出来了：非对称只干一件事——把会话密钥安全递过去；其余数据全交给对称。

更进一步，现代 TLS 1.3 用的是 ECDHE，不是「用公钥加密密钥」，而是双方各出一对临时密钥、交换公钥、各自算出同一个共享密钥。这是密钥交换，不是密钥传输。

ECDHE 的 E 是 ephemeral（临时），用完即弃。所以有了前向安全：服务器长期私钥哪天泄露了，历史流量也解不开。

六、还差最后一块：这个公钥到底是谁的

非对称解决了「密钥怎么安全到对方」，但没解决「这个公钥是不是真的是他的」。中间人完全可以给你自己的公钥。

这一步交给证书：服务器出示证书，证书由 CA 私钥签名，客户端用系统内置的根证书一级级验上去，验到可信为止。

所以三句话收口：

  • 非对称负责递钥匙
  • 对称负责干活
  • 证书负责证明钥匙是谁的

七、一句话总结

HTTPS 加密的是 HTTP 的语义，不加密的是把包送到目的地所必需的元信息。

想连域名都藏住，得靠 ECH（加密 SNI）+ DoH（加密 DNS 查询），那是另一层的事了。
